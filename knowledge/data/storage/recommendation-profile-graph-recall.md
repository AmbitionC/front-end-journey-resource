动态用户画像描述“当前能依据哪些信息理解这个用户”，图谱描述“用户、物品、类别等实体之间有哪些关系”。二者可以共同服务推荐，但画像不一定直接返回候选物品，图数据库也不自动完成推荐排序。设计时先明确任务、数据职责与依赖，再决定哪些链路能够并行。

## 先把召回、排序与展示分开

推荐任务的输出通常是供用户选择的物品、内容或行动候选。一个常见系统先从大集合生成候选，再评分排序，最后结合约束与多样性调整展示结果。[Google 推荐课程](https://developers.google.com/machine-learning/recommendation/overview/types)将这些阶段分别讨论，不能把“查到了候选”直接当成“推荐已经有效”。

| 阶段 | 回答的问题 | 典型产物 |
| --- | --- | --- |
| 用户理解 | 当前意图、长期偏好与硬约束是什么 | 带来源和时间的特征或状态 |
| 候选生成 | 哪些物品值得进入后续比较 | 物品 ID、来源与召回依据 |
| 评分与重排 | 候选怎样比较，哪些能展示 | 可追踪的排序与最终列表 |

用户画像可以用于形成检索条件、选择召回通道、提供排序特征或解释结果。图谱可以用于沿关系找候选，也可以只提供关系特征或约束。先画清具体用途，再判断它们是不是“两路召回”；不能从名称直接得到这个结论。

推荐也不等同于 GraphRAG。后者通常组织文本中的实体关系与来源证据来支持问答；推荐则要定义物品集合、用户任务、交互信号与候选排序目标。使用了图结构，不代表两套任务的标签、评价指标或输出合同相同。

## 动态画像保存什么

画像是对用户信息的一种任务相关表示，可以是结构化属性、近期行为汇总、意图标签、概率特征或学习表示。标签目录的大小、存储字段数与模型 embedding 维度是不同概念。具体表示应由查询和更新需求决定。

先区分三类信息：用户明确给出的要求、可观察的行为事实，以及模型推断出的偏好。用户说“不再看这个类别”与系统根据一次浏览推断“可能喜欢这个类别”，可信度和处理规则不同，不应混成不可纠正的用户事实。

下面是教学数据合同，字段和数值只用于说明来源边界，不是行业标准或实际用户记录：

```json
{
  "subjectId": "u-demo",
  "profileVersion": "p-7",
  "asOf": "t-cutoff",
  "signals": [
    {
      "name": "preferred_category",
      "value": "backend",
      "kind": "explicit",
      "sourceRefs": ["event-demo-1"],
      "validUntil": "t-expiry"
    }
  ]
}
```

`asOf` 表示这份视图只使用截至某时刻可获得的信息；它不能靠查询时临时读取未来反馈来补齐。还需在可信系统中绑定主体、授权范围与更新规则，不能接受模型自报的用户身份。用户更正、撤回或删除后，相关画像、缓存和派生索引应按明确合同更新。

特征本身还需要一致的处理方法。原始 ID、文本和时间戳通常不能无条件混用；[TensorFlow Recommenders 的特征处理示例](https://www.tensorflow.org/recommenders/examples/featurization)展示了这些输入的不同转换，并强调训练与服务阶段处理的一致性。这说明要固定特征定义和版本，并不要求所有系统都使用某个框架或同一种表示。

## 图谱表示什么，怎样参与候选生成

图模型先定义实体和关系的含义。例如，教学场景可以有用户、岗位与类别三类节点，以及浏览、明确偏好、属于某类别等关系。边应保留事件时间、来源、适用范围和必要的权重语义；边权是统计量、模型分数还是人工规则，要写清楚。

[Neo4j 的推荐建模教程](https://neo4j.com/blog/developer/recommendation-engine-hands-on-1/)用用户、物品和类别说明协同与基于内容的推荐思路。这里借用关系建模的原理，不规定数据库品牌，也不承诺关系相连就说明用户一定喜欢。

几种可能的图查询含义不同：

| 查询思路 | 可能产生的候选 | 需要防止的问题 |
| --- | --- | --- |
| 沿偏好类别寻找物品 | 同类但尚未展示的物品 | 类别过粗、候选重复或过时 |
| 沿相似交互寻找邻近物品 | 有相关共现关系的物品 | 热门物品占满、曝光偏差 |
| 将关系作为排序特征 | 其他通道已召回的候选 | 把关系特征误当独立召回结果 |

这些是设计选择，不是对任何具体项目的还原。图召回也不必使用图神经网络；规则遍历、预计算邻居、图表示学习等方法的成本和更新方式不同，应先说明希望利用什么关系，再选择实现。

## 两条构建链路什么时候能并行

“分别存储”与“彼此独立”不是同一件事。应把实际数据依赖写成有向图：

- 如果画像和图谱各自消费同一份规范化事件，且都不等待对方的派生产物，可以在共享事件版本与实体标识下并行更新。
- 如果某条图边来自画像推断，例如把画像中的意图变成用户到类别的边，图更新就依赖画像版本，不能再称完全独立。
- 如果画像又使用图邻域聚合特征，需要确定计算顺序或迭代版本，避免循环读到半更新的状态。

判断并行性的依据是读写合同、版本和等待关系，不是架构图上画了两根线。异步更新还要说明何时可见、允许多旧、失败如何补偿，以及线上读到不同版本时怎样处理。

可以把系统组织为“共享事件与实体规范，两种有明确版本的数据视图，在线按各自职责生成条件或候选，再统一验收和排序”。这是一种可检验的工程方案，具体数据依赖仍需按任务确认。

## 在线组合时保留什么证据

请求先取得可信的主体与授权范围，再选择截至当前允许时刻的画像和图视图。画像可形成查询条件，图查询可返回物品候选；其他召回源也可以参与。每个候选保留稳定物品 ID、来源通道、版本与入选依据，合并后再处理资格、重复、时效和展示约束。

[Google 的评分章节](https://developers.google.com/machine-learning/recommendation/dnn/scoring)说明候选可来自用户特征、热门内容或关系图等不同来源，再进入共同候选池评分。不同来源的分数未必可直接比较，图中的跳数、相似度或边权也不能未经验证就当最终点击概率。

推荐列表交给语言模型解释时，模型应使用已获准的候选和可公开依据，不能因生成了一段流畅理由就新增物品、放宽资格或推断不必要的敏感特征。解释是输出的一部分，候选授权与业务约束仍由程序执行。

## 用一个小场景检查依赖

假设用户明确表示偏好某一岗位类别，之后浏览了两个岗位。这是教学场景，不是实际面试项目：

1. 事件入口保存明确偏好与浏览事实，并区分事件发生时间和到达时间。
2. 画像链路更新当前偏好及来源；图链路记录浏览关系与岗位类别。
3. 若图仅消费事件，两条链路可分别推进；若图还要消费画像推断的意图边，就等待相应画像版本。
4. 在线查询可以用画像筛选物品，再合并图关系找到的候选；统一检查过期、重复和用户已明确排除的内容。
5. 记录实际展示与后续反馈，供获准的数据更新和评测使用。

没有点击不自动等于不喜欢：用户可能根本没有看到，或已经完成任务。负反馈也要区分“不相关”“已看过”“现在不需要”等含义。不能把一次反馈无限期固化为用户属性，或把全部未来行为写进历史时点的画像。

## 分开评候选、排序与运行可靠性

先定义推荐任务的成功判据与可接受的失败，再固定数据时点、用户范围、候选资格和特征版本。比较基线时，同一阶段使用同一标签口径；不能拿一个通道的候选召回指标与另一个系统的最终业务指标直接比高低。

- **候选层**：检查相关物品是否进入候选池、覆盖哪些用户与物品、重复及无候选情况。基于交互日志的标签可能受曝光与位置影响，未观察到行为不等于确定负例。
- **排序与展示层**：检查相关性、任务结果、多样性和新鲜度，以及用户明确约束是否被遵守。只提高点击率也可能引入诱导点击；评分目标需要与实际价值对应。
- **工程层**：检查画像和图更新延迟、版本缺失、热点节点、查询尾延迟、重建及回滚。一个来源不可用时，只能采用预先验证的替代路径，不能静默忽略硬约束。

ANN 索引相对精确近邻的 Recall@K、推荐候选相对任务标签的召回率，以及最终推荐的用户效果，回答不同问题。应分别报告，不把“向量查得准”当作“推荐一定有价值”。

## 需要避免的推断

画像不是用户的永久真相；图路径不是喜欢或因果关系的证明；用了图数据库不自动意味着做了 GraphRAG、GNN 或多 Agent。两条链路可以共享事件，也可以存在依赖，必须以真实数据合同判断。

清楚的设计能够逐项说明：用户信息从哪里来，哪些是推断，图边表示什么，哪个步骤产生候选，版本何时可见，结果怎样验收。答不清这些问题时，先补职责和证据，比先选数据库品牌更有帮助。
