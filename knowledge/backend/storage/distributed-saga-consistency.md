多个服务各自提交本地事务时，“接口都成功”不等于拥有一个跨服务原子事务。Saga 用一系列本地事务与业务补偿推进长流程。学习目标是解释失败后的实际业务状态，识别隔离缺口，并为流程选择合适的一致性边界。

## 先缩小真正必须原子的边界

先问规则能否由同一权威存储中的一次事务、唯一约束或条件更新表达。若业务允许跨服务中间态，再考虑消息、Outbox 与 Saga；不要因为代码放在多个仓库就直接采用分布式事务。代码库边界、部署边界与业务事务边界不是一回事。

## 本地提交之后怎样恢复

教学流程先预留库存，再授权支付，最后确认订单。若支付确定失败，可以释放库存；若调用超时，先查询稳定操作 ID 的结果，不能既重复扣款又重复补偿。补偿是一个新的业务动作，可能不是原操作的数学逆，也不抹除已经被外部观察到的事实。[Microsoft Saga 模式](https://learn.microsoft.com/en-us/azure/architecture/patterns/saga)说明了本地事务、补偿、不可逆转折与可重试步骤。

![预留库存后尝试支付，成功则确认订单；确定失败后释放预留，结果未知先对账，补偿失败保留恢复任务](https://font-end-journey-resources.oss-cn-hangzhou.aliyuncs.com/images/distributed-saga-consistency-recovery-v1.png)

实际系统必须区分确定成功、确定失败与结果未知。释放库存、退款或通知都可能再次失败，因此持久化流程状态、尝试记录和待恢复任务，而不是仅在内存里写一个 catch。幂等键、去重与状态机约束防止重复提交和乱序消息越过合法状态。

## 编排与协同各有什么代价

编排由协调者保存流程状态并指挥参与者，路径较集中，但协调服务需持久化、恢复和容量治理。协同让服务根据事件继续动作，简单流程可以减少中心耦合，但参与方增多后因果链、循环依赖与故障定位更难。两者都不能免除业务补偿、幂等和可观测性。

## 除了成本，为什么仍有风险

Saga 没有内建跨服务的全局隔离。其他流程可能看到部分提交状态，或与补偿并发竞争。可以使用业务预留、版本检查、语义锁、状态限制等方式保护特定不变量，但这些措施须逐条说明，不能笼统宣称获得完整串行化隔离。

补偿本身也可能失败；邮件、外部发货等动作可能不可完全撤回。需要明确不可逆节点、哪些步骤可安全重试、恢复期限与人工处理条件。流程长、参与服务多或可观测性不足时，中间态持续时间与恢复难度都会增加。

## 怎样选一致性方案

| 条件 | 优先讨论的方向 |
| --- | --- |
| 同一数据库内必须立即成立的规则 | 本地事务、约束与条件更新 |
| 业务提交与待发消息必须共同记录 | 事务 Outbox，消费者仍幂等 |
| 跨服务长流程，允许显式中间态与补偿 | Saga，明确状态、隔离和恢复 |
| 跨参与者严格原子，且资源支持相应协议 | 核对分布式提交协议及阻塞、可用性和运维代价 |

这是选择问题的检查顺序，不是所有系统的固定优先级。设计前写清“什么状态允许被看到、多久必须恢复、哪些操作不可逆”，再对超时后成功、重复消息、补偿失败和并发订单做故障演练。
