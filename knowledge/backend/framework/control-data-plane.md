控制平面决定系统应该怎样运行，数据平面承担真实流量与工作执行。学习目标是把一条策略从配置到生效追踪清楚，区分管理操作成功与请求已经执行，并说明控制服务失联时的边界。

## 为什么拆开两种责任

以教学模型网关为例，配置模型路由、额度与部署策略属于管理责任；接收请求、执行授权、选择后端并转发结果属于请求路径。把频繁请求和低频配置分开，有助于分别扩缩容、设置权限与故障恢复。但一个实际组件可能同时包含两种职责，不能只按服务名字判断。

## 用 Kubernetes 校准概念

[Kubernetes 组件说明](https://kubernetes.io/docs/concepts/overview/components/)将 API Server、etcd、调度器与控制器等列为控制平面组件，将 kubelet、容器运行时等列为节点组件。控制器协调实际与期望状态，节点执行工作；这说明“决定与协调”不等于“亲自完成每一次业务请求”。节点组件也不全是狭义网络数据转发器，应按具体系统解释数据平面的范围。

## 从配置成功到策略生效

配置写入后，执行端可能尚未接收、校验或切换新版本。应分别记录已提交版本、执行端已接收版本与实际生效版本，并为传播延迟和失败提供观测。多节点切换还要定义是否允许短暂版本不一致，旧版本何时失效以及如何回滚。

模型服务、AI 开发工具与上层应用是另一条“能力分层”轴：模型层提供推理能力，开发工具组织数据、评测与编排，应用层承载具体用户任务；这是解释责任的示例，不是某公司的实际组织或唯一层级。这些层都可能各有控制与执行职责，不能把“模型层=数据面、工具层=控制面”强行一一对应。

## 控制服务断开后会怎样

执行端可以按已验证的缓存策略继续部分工作，也可能对需要实时授权的动作拒绝或降级。选择取决于权限撤销、策略有效期和业务风险；“控制面故障不影响数据面”不是普遍保证。凭据、租户与审批范围仍须由受信任执行端检查。

检查时追踪一次策略变更：谁有权提交、哪个版本被验证、哪些节点已生效、异常如何回退。再测试管理服务不可用、执行节点重启和旧策略过期，核对实际请求行为，而不只看管理 API 返回成功。
