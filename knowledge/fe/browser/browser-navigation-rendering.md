浏览器把一次导航转成页面显示，需要解决三个不同问题：怎样取得资源、怎样把资源解析成页面结构、怎样把结构转换成像素。可以用这条责任链组织回答，但不能背成每次都发生、严格串行的一张固定时间表。

## 导航、资源和页面状态

输入 URL 或点击链接可能启动导航，但不一定创建全新文档。例如，同一文档内的片段跳转与完整加载不同；缓存和已有连接也会改变实际路径。以下以获取并显示一个新 HTML 文档为主，具体浏览器内部进程布局不作为通用前提。[MDN：页面加载阶段](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/How_browsers_work)。

URL 中的协议、主机、路径与查询参与定位请求；片段主要用于文档内定位，不是服务器请求路径的一部分。取得主文档后，还可能发现 CSS、脚本、图片等其他资源，它们的请求与解析会交错进行。

## 从名称与连接到响应字节

需要访问网络且没有可复用结果时，系统解析域名并取得目标地址，再建立或复用连接，发送 HTTP 请求，处理响应状态、头部和内容。缓存命中、重定向、连接复用等都可能改变这段工作，不能把一次冷启动的步骤套给所有请求。

HTTPS 涉及安全连接，但也不能一概说“所有 HTTP 都先走 TCP 三次握手”。HTTP/3 使用 QUIC；协议和已有连接状态会影响建立过程。面试中可以先说明传统 HTTPS over TCP 的路径，再明确适用条件，不编造统一握手耗时。[RFC 9114：HTTP/3 与 QUIC](https://www.rfc-editor.org/rfc/rfc9114)。

响应成功还不代表页面已可交互。服务器生成内容的耗时、下载时间、解析工作和后续脚本执行，是需要分别观察的成本。

## 从文本到结构与样式

浏览器解析 HTML 形成 DOM，处理 CSS 得到样式规则，并据此计算元素应使用的样式。HTML 可以逐步解析，提前发现的资源也可以提前请求；浏览器不必等所有图片和脚本下载完才开始所有工作。

JavaScript 可能读取或改变 DOM 与样式，因此脚本的加载、执行时机和解析会相互影响。不能把“有 JavaScript”概括成全部资源都被阻塞，也不能假定各种脚本加载属性等价。定位问题时，应核对实际文档顺序与执行条件。[Chrome：渲染器中的解析、样式与脚本](https://developer.chrome.com/blog/inside-browser-part3)。

DOM 描述结构，样式计算决定表现，二者尚不足以确定最终像素位置。还需要布局以及后续绘制工作，才能形成可显示结果。

## 布局、绘制与合成各做什么

布局确定元素的几何信息，绘制产生绘制内容或指令，合成则把相应结果组织成最终帧。这里是责任划分，不要求所有浏览器以完全相同的线程或数据结构实现。

改变文字或尺寸可能影响布局；某些只影响表现的变化可能主要触发后续工作。实际是否能够复用已有结果，取决于属性、内容及实现，不能保证某个动画在任何页面上都不会产生昂贵工作。[Chrome：布局、绘制与合成](https://developer.chrome.com/blog/inside-browser-part3)。

一帧能显示也不代表加载过程完成。后续资源、脚本和用户输入会继续更新页面。长任务可能占用主线程，让用户已经看到页面却不能及时操作；这与首批 HTML 的网络耗时不是同一个瓶颈。

## 把机制用于定位问题

若响应首字节迟迟不到，先区分服务器计算、连接与网络等待；若 HTML 很快却长时间空白，检查关键资源、解析和执行；若已显示但点击延迟，查看主线程任务与交互处理；若滚动卡顿，再检查每帧的布局、绘制和合成成本。

这些是诊断方向，不能只凭现象判定唯一原因。用浏览器网络和性能轨迹核对发生顺序，比较相同设备、页面状态与负载下的变化。缓存状态和连接是否预先建立，也应写进测试条件。

## 面试口述与条件变化

可以这样回答：“我按资源获取、解析样式、布局绘制合成来说明责任链。新文档的冷加载可能涉及 DNS、连接与 HTTP，但缓存、连接复用、HTTP/3 和同文档导航会改变路径。资源加载、解析与脚本可以交错；可见、加载完成和交互就绪要分别测量。”

以下为教学追问：

- 第二次打开页面为什么不能直接复述首次网络步骤？先检查缓存、连接复用和页面生命周期，实际工作可能减少或改变。
- 响应很快但点击仍慢，应只优化接口吗？应核对脚本和主线程交互任务；网络完成不能证明交互就绪。
- DOM 已建立，为什么还不能说所有像素已确定？样式、布局及后续绘制合成仍有独立职责，后续更新也可能改变结果。
