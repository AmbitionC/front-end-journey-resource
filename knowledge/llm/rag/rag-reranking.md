召回器从大语料中快速找出可能相关的候选，重排器在这个较小集合中比较哪些文本真正回答了问题。重排可以把低位证据上移，却不能找回候选池之外的文档。是否采用 Cross-Encoder，要验证它在业务问题和固定候选池上的收益，而不能从模型结构直接推出“必然更准确”。

## 一个退款问题为什么容易排错

假设用户问：“企业年付套餐用了两个月，现在还能退款吗？”系统只能查询该用户获准访问的现行政策，答案要区分套餐、使用状态及适用时间。已有混合召回得到三个块，初始排序为 B、A、C：

| 块 | 主要内容 | 对本问题的作用 |
| --- | --- | --- |
| A | 个人月付套餐退款流程 | 词语相关，套餐不符 |
| B | 企业年付套餐，未启用时可按规则退款 | 套餐匹配，使用状态不符 |
| C | 企业年付套餐，已使用两个月的退款限制 | 同时回答套餐与使用条件 |

这是教学设定，假设 C 的政策明确且当前有效；没有运行具体模型。朴素方案只取初始 top-1 的 B，会让生成模型引用“可退”却忽略未启用条件。先取更多候选再重排，是把模型计算预算集中在 B、A、C 的完整条件上。

两阶段的因果链是：第一阶段用倒排索引或可预计算向量产生候选，第二阶段为每个查询—候选对打分，再由运行时按分数排序、按上下文预算选证据。[Sentence Transformers 的 Retrieve & Re-Rank 文档](https://sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)给出这种管线（滚动文档，核验于 2026-10-02）。如果 C 根本没进候选池，换重排器仍不能解决该次问题，应先检查切块、过滤、检索表达或候选深度。

## Cross-Encoder 比双塔多看到了什么

双塔（Bi-Encoder）分别编码查询与文档，再比较两个向量。文档向量可以预计算，因此适合大规模候选查找；查询与文档的具体词对关系要压缩进固定向量。交叉编码器（Cross-Encoder）把查询和一个候选一起送入网络，允许查询 token 与候选 token 在 attention 中交互，再输出该文本对的相关性信号。它不能像双塔那样把文档单独编码成可复用的检索向量。[Cross-Encoders 文档](https://sbert.net/examples/cross_encoder/applications/README.html)解释了这一结构差异（滚动文档，核验于 2026-10-02）。

在本例中，联合输入给模型机会对齐“企业年付”“用了两个月”与 B 中“未启用”、C 中“已使用”的条件关系，而不仅是主题相似。机会不等于保证：模型可能没学会业务缩写，忽略否定词，或因输入截断看不到 C 的限制条款。双塔也可能已经把 C 排在首位；此时新增计算未必改善最终答案。

与所有文档逐对做联合计算通常比查询一次预计算向量索引昂贵，因此只对 top-K 候选使用。候选数量、文本长度、硬件、批处理和服务排队都会影响耗时，不能给出通用“慢几倍”结论。

## 预训练目标为何可能与业务目标错位

“预训练 Cross-Encoder”常被混用。基础语言模型预训练并不自动教会相关性排序；公开 reranker 往往在基础模型上又用查询—段落相关性数据训练。接入前应查具体模型卡：语言、训练数据、目标、输入限制、输出语义与许可证，不能把所有模型当成同一种评分器。[Sentence Transformers Rerankers 文档](https://sbert.net/examples/cross_encoder/training/rerankers/README.html)展示了成对标签、正例或列表数据及不同训练方式（滚动文档，核验于 2026-10-02）。

即使训练目标都是“相关”，标签含义也可能不同：通用检索只要段落能帮助回答就算相关，本业务却要求适用套餐、已使用状态和政策时效同时满足。本例的 B 很像标准问答正例，却不适用该用户。其他偏移包括语言、内部缩写、文档格式和负例难度；训练时只见过无关主题负例，就未必能区分同主题的条件错配。

[BEIR v4](https://arxiv.org/abs/2104.08663v4)用异质任务和领域研究域外检索泛化，说明不能只看单一同域基准。它的结果不是某个业务模型的性能保证。这里“业务域偏移会带来风险”是从该研究及训练目标差异得出的应用判断，风险大小需要本地标注和实验确认。

## 如何在固定候选池上证明排序改进

先用业务规则和人工标注确定各候选的相关性，冻结查询、候选 ID、文本、权限、时效过滤、模型版本及文本预处理。对同一份候选池比较初始排序、预训练 reranker、必要时业务适配后的 reranker；候选数量和内容不能同时变化，否则分不清改进来自召回还是排序。

本例只有 C 是能直接回答该条件的证据。假设重排结果变成 C、B、A，那么单个查询的首个相关结果排名从 3 到 1，倒数排名从 1/3 到 1。这只是对假设排序的机制演算，不是模型效果报告。多个查询才可计算 MRR；有分级相关性时用 nDCG@N 比较前 N 的排序质量；Precision@N 看选入块中多少相关。与此同时单独计算召回 Recall@K，确认正确证据有没有进入候选池。

验证应按真实业务情况切片：套餐和状态条件、否定词、缩写、语言、长块、精确编号、多跳问题。看 C 是否上移，也看多少原本正确的查询被重新排错。校准和调参使用开发集，验收使用按业务情境或文档组留出的数据，防止相同政策的改写泄漏到两边。

如果预训练模型整体不差，却在“已使用/未启用”切片退化，先检查截断和输入缺上下文，再考虑业务适配。标注查询、适用正例和同主题但条件不符的困难负例；不同模型支持的损失与训练接口不同，不把某一种损失当通用配方。改训后仍需在相同候选池和留出集比较，不能把开发集更高分当成已解决域偏移。

最后固定生成模型与上下文预算，评答案正确、忠实度、引用适用性、任务完成、延迟和费用。排名变好却选入多个重复块，或导致关键多跳证据被挤出，可能让最终答案退化。只有排序层和端到端证据都支持，才有采用依据。

## 输入、分数和候选深度怎样共同影响结果

K 太小可能漏掉 C；K 增大可能提高覆盖，也增加重排计算和更多条件相似的噪声。N 受上下文预算限制，两者都应在自己的质量—资源曲线上选择，而非照抄固定参数。块要能独立判断适用性，本例 C 至少要保留标题、套餐、使用条件和政策版本；只截出“不可退款”会失去作用对象。

重排分数不是事实正确概率。不同模型可能输出未归一化实数或有界值，[Rerankers 文档](https://sbert.net/examples/cross_encoder/training/rerankers/README.html)也明确存在不同范围；不能把所有输出都解释成 0–1 概率，也不能永久规定 `score > 0.8`。同一查询内的排序较直接，跨查询筛选阈值仍须按业务标签校准。模型或预处理升级后，分数分布、截断行为与排名都应重核。

元数据可帮助判断相关性，但租户授权和现行政策范围应由检索及应用层强制执行，不能让模型凭分数决定用户能看什么。下面是接口无关的伪代码，未在完整环境运行，不对应某家供应商 SDK：

```text
candidates = retrieve(query, enforced_scope, candidate_depth)
inputs = [(query, permitted_text_with_context(c)) for c in candidates]
scores = score_pairs(inputs, pinned_reranker)
assert score_count_matches_candidates(scores)
ranked = stable_sort_pairs(candidates, scores)
evidence = select_with_dedup_and_budget(ranked, context_budget)
answer = generate_from_evidence(query, evidence)
```

运行时持有候选 ID 与得分的映射。批处理或异步返回时要用稳定 ID 对齐，不能把乱序结果按数组位置绑定错误文档；schema 合法也不能发现这种语义错配。

## 重排之后为什么还要选上下文

最高分的几个块可能重复同一政策。可在相关性范围内去重、限制单文档块数、合并相邻段落，保留其他子问题所需证据。本例若问“可退吗，若不能退还能转套餐吗”，退款限制与套餐变更规则都需要；仅给每个块独立打分可能低估组合价值，可按子问题检索和分配证据预算，再测端到端效果。多样化不能强塞无关内容。

生产运行还需超时、批大小、并发和输入长度限制。缓存键应包含查询、候选内容 hash、授权范围、预处理和模型版本；用户权限变化时要失效，不能跨租户复用未经隔离的证据。超时可按业务风险退回原始排名、明确证据不足或延后回答，并记录降级；并非所有任务都适合相同策略。

如果候选已经很准、延迟预算很紧，或固定候选评测没有排序收益，可以保留一阶段检索。如果 C 经常未召回，先修召回；如果 C 已在池里却被条件不符的 B 压住，才是验证 reranker 或领域适配的明确问题。这样的条件能解释为何选择一个方案，而不是简单说“两者各有优劣”。

## 面试口述短答

“我先召回候选，再用 Cross-Encoder 联合查询和候选做交互打分，它有机会识别双塔压缩后容易漏掉的条件关系，但不保证业务上更好，也救不回漏召回。预训练 reranker 的相关性标签可能不符合业务适用条件，所以我冻结候选池、用独立业务标注比较排序和条件切片，再固定生成预算验证答案与引用。必要时加困难负例适配；收益不足或延迟不满足时，就保留简单基线。”

## 教学补充：改变条件的模拟追问

以下是教学模拟，不代表原面经逐字提问。

1. **正确政策没有进 top-K，但换了更大的重排器，为什么没改善？** 要点：候选池是能力边界；先检查权限/时效过滤是否正确、切块和 Recall@K，再优化排序。对应“两阶段”。
2. **整体 nDCG 上升，企业年付条件题却变差，如何决定接入？** 要点：固定候选池检查域偏移、截断和困难负例，保留重要切片门槛，再测答案质量；平均提升不足以接受关键切片退化。
3. **固定候选池排序变好，最终回答仍漏了套餐变更规则，问题在哪里？** 要点：查上下文预算、去重和多子问题覆盖，联合证据需求不等于单块高分；保持生成模型一致做端到端消融。对应“上下文选择”。
