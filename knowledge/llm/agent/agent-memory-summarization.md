会话摘要是有损压缩，不是原始事实的新版本。它的目标是在有限上下文中保留继续任务所需的信息，同时让关键决定回到原始消息、文件或工具证据。可靠设计要回答两件事：压缩丢了字段时如何发现，异步摘要迟到时怎样不覆盖后来状态。

## 用一次延期决定看见摘要风险

假设主 Agent 帮用户准备 beta 发布资料，子 Agent 核对条款。会话中先有“5 月 15 日发布”，后有“改为 5 月 22 日”；条款 v2.1 已获确认；用户又强调“现在只整理材料，不发布”。这是教学设定。

滑动窗口只保留最近几轮，可能丢掉条款版本。自由摘要“beta 已准备好，条款通过”虽然流畅，却可能遗漏日期修正和禁止发布。子 Agent 一旦基于这句话工作，会把上游遗漏当成事实。长上下文也不能保证每条信息都被正确使用：[Lost in the Middle](https://arxiv.org/abs/2307.03172)在所研究的问答和检索任务、模型条件下发现，相关信息的位置会影响利用效果；这不意味着所有当代长上下文模型都必然出现同样幅度的退化。

先定义保留契约：当前目标、有效约束、最新决定、未完成任务、精确实体与版本、来源、冲突和结果未知的工具调用。寒暄可以压缩，否定词、单位、日期、版本和授权条件不能靠“通常不重要”丢弃。摘要用途也要区分：交接摘要保任务状态，长期记忆保可复用事实，用户可读摘要解释经过，不能用一个通用短段承担所有责任。

## 原始记录、事实和工作视图怎样分层

原始时间线保存用户消息和工具结果；事实层提取带来源的字段；工作摘要只是给当前模型使用的紧凑视图。摘要更新不能覆盖原始记录，也不应只反复总结上一版自然语言而失去证据回链。以下为应用层数据结构示意，未在完整环境运行：

```ts
type SummaryFact = {
  id: string;
  key: string;                 // 如 launch_date、allowed_actions
  value: string;
  sourceMessageIds: string[];
  scope: string;               // 对哪个任务、实体、时间有效
  status: 'confirmed' | 'inferred' | 'disputed';
  supersedes?: string;         // 新决定替代哪个旧事实
};
```

本例事实层保存 `launch_date=May22`，引用改期消息，并标明替代 May15；保存 `terms_version=v2.1` 及确认来源；把“只整理、不发布”写入动作约束。原来的 May15 仍能追溯，但不作为当前决定。若“它已经通过了”指的是条款还是支付接入不明确，先解析关联消息；无法消解则标不确定，不能任选一个实体。

## 一次同步压缩怎样安全替换上下文

[LangGraph 的 Summarize messages 小节](https://docs.langchain.com/oss/python/langgraph/add-memory#summarize-messages)展示了扩展 summary 状态、移除旧消息的模式（滚动文档，核验于 2026-10-02）。下面的质量门和一致性协议是应用层补充，不是框架默认保证。

同步压缩在下一次模型调用前等待摘要完成。运行时持有消息序号和摘要版本，冻结待压缩前缀，比如消息 1–40；提取事实并解析指代；把新事实与既有事实合并，识别替代与冲突；生成结构化视图，再派生短自然语言。随后校验所有关键约束、未完成任务及引用，保存新的摘要与覆盖范围，最后才从活跃上下文移除该前缀。

本例必须检查新视图包含 May22、v2.1、只读整理和子任务未完成项。字段不存在、来源 ID 不可访问、值与源记录不一致都应阻止替换。校验“有 launch_date 字段”只能发现缺项，不能发现日期错写成 May15；还要对照有效决定及来源。关键机器字段宜由结构化状态直接注入，不经过模型重写。抽取式保原句更忠实，结构化方式便于校验，生成式说明更易读，可在同一管线组合使用。

摘要失败时保留原消息。若上下文已无法容纳，停止发起新的大调用，缩小待处理区间、保留关键原文或返回阻断；“先删旧消息、稍后补摘要”会让失败后无从恢复。保留最近消息还要保持工具请求与结果配对，避免只留下一个无法解释的工具响应。

## 异步压缩为什么会出现迟到覆盖

异步方式让摘要任务在后台处理冻结前缀，主会话继续。它减少等待，却需要明确读写协议。考虑如下时序：

| 时刻 | 主会话状态 | 后台任务 |
| --- | --- | --- |
| t0 | 摘要 S7 覆盖到消息 20；消息 21–40 已存在 | A 基于 S7 冻结 21–40，认为日期是 May15 |
| t1 | 消息 41 改期为 May22；42 重申不发布 | A 仍在生成旧前缀摘要 |
| t2 | 更新任务 B 合并到 42，提交 S8 | B 完成，当前日期为 May22 |
| t3 | S8 已有效 | A 迟到，若无条件写回就覆盖 S8 |

问题不在“后台一定慢”，而在把旧快照的产物当成最新整段状态。可以把提交设计成比较交换：A 携带 `base_summary_version=7` 和 `covered_until=40`，只有当前摘要仍为 S7 且校验通过，才原子提交；版本已变时丢弃 A 或基于 S8 重新计算，不能直接覆盖。比较版本、写摘要和更新覆盖游标必须处于同一原子操作，分开做仍会竞态。

即使 t1 没有 B，A 成功压缩到 40，也只能移除已覆盖的前缀；消息 41–42 要继续留在尾部。下一次模型看到的是“截至 40 的摘要 + 41 之后原文 + 最新结构化约束”，而不是把旧摘要宣称成当前全状态。跨轮约束如“不发布”可以单独置于高优先级状态，避免后台视图滞后影响工具执行。

这是版本化前缀压缩方案的机制推演，未在完整存储/并发环境运行；它不意味着仅加一个 `version` 字段就已解决一致性。若不能实现原子提交，或任务特别短、延迟预算充足，同步方案更容易保证交接一致。异步队列若持续落后，则要限队列、合并重复请求或暂停继续增长的工作；后台并非无限容量。

## 主子交接与恢复怎样检查

父 Agent 向子 Agent 传“任务契约 + 最新事实 ID + 摘要覆盖范围 + 必要原文”，不要只传一段故事。本例子任务只需要条款 v2.1、核对目标、截止时间与只读边界；其他发布营销细节可以省略。子任务返回已确认事项、证据 ID、未决项及输入版本。父运行时发现结果基于旧条款时，决定重查或明确标为过期，不能默默并入当前结论。

[LangGraph Persistence 文档](https://docs.langchain.com/oss/python/langgraph/persistence)把线程状态 checkpoint 与跨线程 store 区分开（滚动文档，核验于 2026-10-02）。checkpoint 可以保存摘要版本、覆盖游标、事实和任务状态，但独立 thread ID 不等于租户权限隔离；跨线程共享 store 的读取范围仍由应用控制。

恢复时验证原始引用可访问、文件版本或内容 hash 是否变化，以及工具是否真的完成。不要在一次写操作结果未知时压缩掉请求 ID、调用参数和响应；“没有看到成功”与“没有发生”不同，重试决策需要原证据和幂等信息。

## 怎样判断压缩没有破坏后续任务

压缩率只衡量短了多少。准备包含改期、撤回决定、同名实体、数值单位、失败调用和主子交接的长对话样本，比较压缩前后继续任务的事实正确、约束遵守、证据可追溯和恢复行为，再连续压缩多轮观察误差累积。异步还要覆盖 A 晚于 B、压缩期间追加消息、校验失败、提交失败和重启恢复等顺序。

观测可记录摘要版本、覆盖区间、输入/输出 token、关键字段遗漏、引用失效、版本冲突、重新读取原文次数。覆盖率应按任务必要信息加权：把“不发布”保住，比把每句寒暄保住更有价值。独立 verifier 可以补充检查，但必须能看到源记录；让两个模型只读同一错误摘要不会恢复丢失的信息。

## 面试口述短答

“我把摘要当带版本的视图，原始消息和机器必需的约束独立保留。压缩时冻结前缀，提取带来源事实，检查日期、否定约束、未完成任务和引用，保存后才移除已覆盖消息。同步方式等摘要完成；异步方式携带基准版本，原子比较交换提交，迟到摘要不能覆盖新版本，未覆盖尾部继续保留。字段缺失就回读原文或阻断交接，不能让子 Agent 猜。”

## 教学补充：改变条件的模拟追问

以下是教学模拟，不代表原面经逐字提问。

1. **摘要包含条款版本字段，但值是旧版本，schema 检查都通过了怎么办？** 要点：结构有效不等于事实有效；对照最新确认消息、替代关系和来源，过期结果回查。对应“同步压缩”。
2. **后台摘要只覆盖到 40，用户在 41 撤回发布授权，能直接使用新摘要吗？** 要点：可以作为前缀视图，但必须连同 41 之后尾部与最新权限状态使用；旧摘要不得授权工具。对应“异步竞态”。
3. **没有原子条件更新能力，业务又不允许交接旧约束，还要异步吗？** 要点：先选同步或单写者串行提交协议；并发低延迟收益不能替代一致性要求，版本字段本身不够。
