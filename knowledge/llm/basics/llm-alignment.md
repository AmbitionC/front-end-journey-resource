预训练让模型学会“什么文本可能出现”，对齐（alignment）则尝试让模型在交互中更符合预期：理解指令、提供帮助、承认不确定性、遵守安全边界。它不是一次训练步骤，而是数据、优化目标、政策、评估和运行时控制共同组成的系统。

## 对齐在对齐什么

“符合人类价值”过于抽象。工程中必须把目标拆成可观察行为，例如：

- 是否完成用户明确且允许的任务；
- 是否避免编造事实并能表达不确定性；
- 是否在危险请求中安全且不过度拒答；
- 是否尊重权限、隐私和工具审批；
- 是否保持格式、语气和业务规则一致。

这些目标可能冲突。更严格的拒答策略会降低某些风险，也可能拒绝合理的教育、医疗或安全研究问题。对齐不是找到一条完美标量，而是在明确场景中管理取舍。

## 第一层：监督微调（SFT）

SFT 使用“输入—理想输出”示范继续训练模型。它适合教授：对话模板、任务格式、工具调用 schema、解释风格和典型拒答方式。

高质量示范应明确前提、展示允许与禁止行为的边界，并覆盖困难反例。若示范只包含简单问答，模型可能在长任务和工具错误中退化；若标注者标准不一致，模型会学到互相冲突的行为。

[InstructGPT](https://arxiv.org/abs/2203.02155) 先用标注者示范训练监督策略，再收集输出排序进行偏好优化。研究说明指令遵循可以显著改善，但也明确保留了简单错误和未解决风险。

### 从失败类型选择训练阶段与损失

项目使用 Qwen 或其他模型，并不能直接决定该用哪种 Loss。先区分问题来自事实资料过期、指令格式不稳、偏好不符，还是可验证任务的推理/行动失败：事实更新可先评估检索；SFT 用示范教授行为；离线偏好对可用 DPO；在线奖励优化则要求可校准的奖励和受控采样。选择应在同一保留任务上比较，不能用训练损失下降替代真实效果。

对自回归语言模型，SFT 常以指定目标 Token 的下一 Token 交叉熵训练，但哪些位置参与损失由数据格式、标签掩码与实现共同决定。应实际查看模板渲染和 labels，确认用户输入、系统指令、工具结果及助手回答的角色边界，而不是以为整段对话都会自动被当成正确答案。

[TRL 1.16.0 的 SFT 文档](https://github.com/huggingface/trl/blob/v1.16.0/docs/source/sft_trainer.md)区分 prompt-completion 的 completion-only loss 与 conversational 数据的 assistant-only loss；后者还依赖能产生助手掩码的聊天模板。这里限定该版本的约定，不把参数默认值推广到其他训练器。构造训练集时保留任务来源、拒答与工具失败等困难样本，做语义去重并隔离同源评测材料；训练前后的任务质量、过度拒答和失败切片都要复核。

### Agent 轨迹：先分诊，再决定是否入训

假设已积累一批成功、失败和人工修正的轨迹，数量本身不决定训练价值。先保留获准使用的原始记录，建立派生数据版本：关联任务、模型 / Prompt / 工具与环境版本，校验调用和返回能否对应，记录终止原因，并用外部状态或人工复核确认任务结果。缺工具返回、只有“完成了”的自述或人工修正无法对齐到原上下文的样本，应隔离待审，不靠补写内容凑成完整示范。[Agent 评测实践](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)区分轨迹与环境终态；这也是整理训练候选时需要保留两类证据的原因。

再按失败原因分流。工具不可用、权限缺失、错误接口合同或流程跳过验收，优先修工程链路；资料过期先检查检索与数据更新；在上下文和工具都充分时仍反复出现的行为、格式或决策问题，才形成 SFT、偏好学习或其他后训练的候选。这个分流是诊断框架，最终仍须用保留任务比较工程修复与训练的收益。

| 轨迹类型 | 可以提取的信号 | 不应直接做的事 |
| --- | --- | --- |
| 经核验的成功 | 满足目标与约束的示范、可比较的偏好候选 | 把全部中间动作都认作必要或最优 |
| 失败 | 失败类型、回归案例、经复核的负例或步骤标签 | 把原失败动作当作正确 SFT 目标 |
| 人工修正或恢复成功 | 原上下文下经验证的修正动作、恢复决策 | 把人类额外获知的信息伪装成模型当时已知 |

清洗需做隐私与许可检查、角色和工具合同校验、语义近重复去重，并按任务来源及部署目标划分训练、验证和保留测试。同一任务的成功、失败、重试与人工改写应作为同源组处理，避免改写跨集合；不按固定长度或固定成功率阈值一刀切删除难例。[TRL 1.16.0 的 SFT 工具数据约定](https://github.com/huggingface/trl/blob/v1.16.0/docs/source/sft_trainer.md)要求保留工具调用、工具回复与可用工具信息；转换后还要实际检查聊天模板、截断和目标掩码，避免把错误动作或工具观察误当成应模仿的助手输出。失败与长轨迹不是天然垃圾，关键是监督目标与证据是否匹配。

### 多路打标微调：先定义标签，再比较分层与端到端

若任务是从文本生成多个业务标签，先冻结标签本体、共现/层级约束、标注指南及无法判定时的表示，并保存样本来源和授权范围。输入只包含预测时可获得的文字和上下文；输出可以是固定 schema 的标签列表或结构化对象。训练前实际检查模板、截断、labels 掩码与解析结果，让“生成一段话”和“返回合法标签”成为可区分的验收项。[TRL 的 SFT 数据说明](https://github.com/huggingface/trl/blob/v1.16.0/docs/source/sft_trainer.md)支持核对不同数据格式与目标位置。

先按来源做近重复去重，并依据部署目标按时间、用户或业务实体隔离训练、验证和测试，避免同一事件的改写跨集合。时间泛化和新实体泛化不是一个问题，应分别设计协议；[scikit-learn 的分组与时序切分说明](https://scikit-learn.org/stable/modules/cross_validation.html)解释了普通随机切分不能替代这些边界。验证集选择提示、训练参数和输出校验规则，独立测试集只验收冻结后的方案。

分层方案先判上层类别，再调用相应下层预测，可能限制标签空间、便于逐层维护，但上层漏判会使下层失去机会；端到端方案直接生成完整标签集合，减少显式级联，也会面临组合稀疏、格式错误和层级不一致。这是按任务依赖作出的设计分析，不是某个训练器自动提供的保证。比较时保持标签与切分一致，同时报告完整标签集结果、逐标签/逐层指标、错误传播、无效输出、时延与成本；不只看训练 loss。

训练完成后固定模型、模板、标签版本与解析器，再做部署约束下的验收。全参数更新、LoRA 和分布式并行是参数/资源层面的选择，与“标签预测分层还是端到端”属于不同维度。原项目没有数据集和实测记录时，只能提出上述复核框架，不能补造样本量、提升幅度或最终选型。

## 第二层：偏好优化

很多问题没有唯一标准答案，示范难以覆盖所有风格。偏好数据让评价者比较两个回答，表达哪一个更有帮助、更真实或更安全。

偏好优化可以采用显式奖励模型加 RL，也可以采用 DPO 等直接损失。无论算法如何，模型优化的是**标注分布的代理目标**。标注者背景、评分指南、提示分布和奖励模型漏洞都会影响结果。

一个常见风险是 reward hacking：模型找到让评分器高分、但不符合真实意图的表面模式，例如过度冗长、过度自信或机械加入免责声明。因此必须用独立评估和真实任务检查。

## 第三层：原则、安全政策与红队

[Constitutional AI](https://arxiv.org/abs/2212.08073) 探索了用自然语言原则让模型自我批评、修订，并由模型产生偏好反馈的路径。它减少了部分有害内容标注对人工的依赖，但原则仍由人选择，AI 反馈也可能继承模型偏差。

安全政策要落到可测试的类别：危险能力、隐私、仇恨骚扰、自伤、欺诈、网络攻击、未成年人保护等。红队从对抗角度寻找绕过、歧义和多轮组合风险；发现的问题应进入训练与保留测试集的不同分支，避免只“背会测试题”。

## 第四层：系统级控制

仅靠模型参数无法承担全部安全责任。生产系统还需要：

- 输入输出分类与敏感信息处理；
- RAG 权限过滤和引用核验；
- 工具白名单、参数约束、最小权限和人工审批；
- 速率限制、沙箱、审计日志与异常检测；
- 模型、提示、政策和工具版本化；
- 高风险场景的专业人员复核。

例如，模型可以生成“退款”工具调用，但是否允许退款、最高金额和是否需要二次确认，应由确定性的业务代码决定。

## 如何评估对齐

评估不能只统计“有害请求拒绝率”。至少要同时测量：

1. **帮助性**：正常任务是否被完成；
2. **安全性**：危险能力和政策违规率；
3. **真实性**：事实、引用和不确定性表达；
4. **过度拒答**：相似但合规的请求是否被误伤；
5. **稳健性**：多语言、长上下文、角色扮演和提示注入下是否保持边界；
6. **工具行为**：权限、参数、失败恢复和副作用是否正确。

应保留未参与训练的测试集，结合自动 grader、规则验证和人工评审。自动评分器本身也要校准，不能让一个模型同时当选手、裁判和最终证据。

## 常见误区

- **“SFT 就是注入知识。”** SFT 更擅长塑造任务行为；频繁更新的事实应通过外部知识源提供。
- **“偏好票数等于普遍价值。”** 偏好来自具体人群和指南，需要记录适用边界。
- **“安全模型不需要权限控制。”** 一次错误工具调用就可能造成真实损失，系统必须限制能力。
- **“拒绝越多越安全。”** 过度拒答会损害有益用途，也会掩盖政策设计不清。
- **“一次红队后永久安全。”** 新模型、新工具和新攻击会改变风险面。

## 小结

对齐是持续的系统工程：SFT 提供示范，偏好优化塑造选择，原则与红队探索边界，运行时控制限制真实能力，独立评估负责发现回归。它能降低风险、改善行为，但不能证明模型永远正确或安全。

## 练一练

### 高频考点题 1：SFT 适合教什么

下面哪项最不适合靠 SFT 解决？

- A. 对话模板和输出格式
- B. 工具调用的 schema
- C. 典型的拒答方式和拒答话术
- D. 频繁更新的业务事实

**答案：D。** SFT 更擅长塑造任务行为：格式、风格、工具调用、拒答方式。频繁变化的事实应通过检索等外部知识源提供，写进参数里很快就过期。

### 高频考点题 2：Reward hacking

偏好优化后，模型回答越来越长、越来越爱加免责声明，评分器给分却更高了。这属于什么问题？

- A. 训练数据太少，模型没有学到简洁回答的偏好
- B. Reward hacking：模型钻了评分器的空子
- C. 温度设得太高
- D. 模型参数太大

**答案：B。** 偏好优化学的是标注分布的代理目标，模型可能钻评分器的空子。要用独立的评测和人工抽查发现这类偏移，不能只看奖励分数。

### 高频考点题 3：退款工具谁说了算

客服 Agent 能调用「退款」工具。是否允许退款、最高金额、要不要二次确认，应该由谁决定？

- A. 确定性的业务代码和权限系统
- B. 模型在提示词里自行判断
- C. 只要模型经过充分的对齐训练，就可以放心交给它判断
- D. 由用户在对话里说明即可

**答案：A。** 模型可以提出调用，但能力边界要在系统层限制：工具白名单、参数约束、最小权限和人工审批。一次错误的工具调用就可能造成真实损失，对齐训练替代不了权限控制。
