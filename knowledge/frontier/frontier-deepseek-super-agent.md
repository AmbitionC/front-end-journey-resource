2026 年 10 月 31 日，DeepSeek Harness 团队发了一篇长文《Super-agent 设计探索：迈向更自主的 Agent 系统》，并开源了一个配套的研究原型。它讨论的问题很具体：模型已经够强了，为什么一个人还是只能同时带几个 Agent 干活。本期把这篇文章讲清楚，重点是它的架构和它自己承认的边界。

> **本期 30 秒版**
> 1. 瓶颈从模型换成了人：文章的判断是，单个任务能做多好取决于模型，同时能推进多少任务取决于人的注意力。作者观察到一个人通常只能同时跟进 3 到 5 个活跃会话。
> 2. 解法是一个常驻的 Router 加一批隔离的 Worker，由事件驱动：Router 只负责和人对话、分派任务，不干活；Worker 干活，不直接对人说话。
> 3. 作者自己的初步实验里，和中性提示词的单会话比，完成时间中位数从 20.4 分钟降到 12.4 分钟，读缓存的 token 约为 3.8 倍；单会话换成优先委派的提示词后是 13.8 分钟，差距主要剩在最慢的请求上。原型里 Agent 主动揽的活默认只记录、不真的动手。

## 1. 它要解决什么问题

**发生了什么**

现在主流的 Agent 产品以「会话」为单位：一个会话做一件事，要同时做几件事就开几个会话，由人来回切换、自己记住每个会话的上下文。文章的原话是：

> 一个人通常只能同时跟进 3 到 5 个活跃 Session。

作者说明这是他们自己的观察，没有给样本。由此得出的判断是：单任务的上限取决于模型，多任务的上限取决于人的注意力。

所以 Super-agent 关注的重点是怎么让人少操心，而不是把单个任务做得更好。文章给它定了四个特征：

| 特征 | 含义 |
| --- | --- |
| 连续 | 不管在聊天工具还是 GitHub 上，感觉对面只有一个 Agent |
| 高效 | 不等上一件事做完就能接下一件，并行推进 |
| 主动 | 不等指令就能动手，没必要的时候保持安静 |
| 持久 | 始终在线，出了异常能自己恢复 |

文章开头就声明，这是工程架构思路的探讨，不是在介绍现有产品功能。作者也说自己没有提出新理论，是把计算机系统里的经典思想用到了 Agent 上。

**和以前有什么不同**

以前优化 Agent，盯的是任务成功率和成本。这篇把优化目标换成了「占用人多少注意力」。配套原型的设计原则写得很直接：尽量少占用人的注意力，尽量多给价值；只在人必须行动或者能用上结果的时候才说话；一次只问一个具体问题。

## 2. 架构：Router 和 Worker 两层，由事件驱动

**两层分工**

| | Router | Worker |
| --- | --- | --- |
| 数量 | 一个，常驻 | 多个，彼此隔离 |
| 职责 | 承接所有和人的交互，分派任务，协调，记忆 | 执行具体任务 |
| 工具 | 不执行任务，甚至可以不给命令行 | 完整的执行工具 |
| 模型 | 作者实践中较轻量的模型往往够用 | 通常配最强的模型 |
| 对人 | 统一由它回复 | 按文章设计不直接对人说话，向 Router 汇报 |

这和常见的「主 Agent 带子 Agent」不一样。文章专门做了区分：团队负责人式的主 Agent 会深入拆解一个任务，再把子任务分下去；Router 不拆任务，只管任务和任务之间的分派。Worker 内部可以再用子 Agent 或 Agent 团队。

**事件驱动**

Agent 不是等人发消息才动，而是由事件触发：群消息、邮件、日程、代码评审评论、CI 结果等。几个关键设计：

- **两级过滤**：先由程序按确定的条件过滤（来源、群、白名单），再由模型按策略判断要不要处理。前一级快而便宜，后一级才花 token。
- **Thread 和订阅**：同一个 PR、同一个聊天话题或同一串邮件算一个 Thread。Worker 订阅某个 Thread 之后，后续事件由程序直接送给它，不再经过 Router；没人订阅的事件才由 Router 判断分派。
- **上下文的放法**：很可能用到的信息直接放进上下文；超出预算或不常用的留在外面，只放引用和摘要，需要时再去取。
- **链式召回**：每个事件、Thread、会话都有编号，取回的结果里带着下一步可查的编号，一跳一跳展开。这是为了缓解 Router 长时间运行后丢信息的问题。

**其他几个模块**

- **异步工具调用**：工具从「调用后等结果」改成「启动后立即返回」，结果做完后作为新事件送回来。这样 Agent 不会被一个长任务卡住。文章说这在 DeepSeek Harness 里已经实现，但没有默认开启。
- **计算、状态、环境分离**：Agent 循环放在无状态的容器里，会话存进数据库，代码仓库这类重状态的执行环境留在原地，由一个轻量的守护进程连接，也支持用户自己的机器。作者说这和 Anthropic 的「大脑和手分离」思路一致，区别在于场景，这里先接的是个人机器。
- **Watchdog**：主系统之外的一个独立会话，定时检查。除了基础设施故障，它还由模型判断 Worker 有没有实质进展、有没有跑偏。
- **主动性**：采用「静默复现并修复」的策略。比如群里有人讨论一个问题，Agent 在后台先复现、找修复方法，确认了问题并且修复简单才把结果交出来，否则保持安静。

**面试里怎么用**

被问「怎么让一个 Agent 同时处理很多任务」或「Router 和主 Agent 带子 Agent 有什么区别」时：

> 主 Agent 带子 Agent 解决的是一个任务怎么拆，任务之间的切换仍然靠人。DeepSeek 的 Super-agent 设计把这层也交给了系统：一个常驻的 Router 承接所有和人的交互，只做分派不做执行，可以用便宜的模型；一批隔离的 Worker 用最强的模型干活，不直接对人说话。整个系统由事件驱动，群消息、评审评论、CI 结果都是触发器，先用程序规则过滤，再让模型判断。Worker 订阅了某个话题后，后续事件直接送给它，不再占用 Router。工具调用改成异步，启动后立即返回，结果作为新事件送回来。

**对应知识点**：[事件驱动 Agent 与异步编排](https://www.agent-journey.cn/knowledge?activeKey=agent-event-driven)、[多智能体协作与适用边界](https://www.agent-journey.cn/knowledge?activeKey=multi-agent)、[Subagent 子智能体设计](https://www.agent-journey.cn/knowledge?activeKey=agent-subagents)、[并发控制、资源隔离与公平调度](https://www.agent-journey.cn/knowledge?activeKey=agent-concurrency)

## 3. 实验数字和它自己说的边界

**实验**

文章对实验的限定语很明确：合成负载、简化环境，只作初步参考。编码工作用一个只消耗时间的工具代替，所以测的是调度和协作，不是执行能力。每次运行约 300 条消息，其中约 20 条是工作请求，每种方案跑 5 次；消息间隔和工作时长按四分之一缩放，模型调用耗时是真实值。

| 方案 | 完成时间中位数 / 95 分位（分钟） | 单次运行读缓存的 token |
| --- | --- | --- |
| Super-agent | 12.4 / 15.7 | 2323 万 |
| Super-agent，去掉事件直通 | 12.6 / 15.5 | 3177 万 |
| 单会话加子 Agent 工具，中性提示词 | 20.4 / 29.5 | 605 万 |
| 单会话加子 Agent 工具，提示词要求优先委派 | 13.8 / 29.0 | 1082 万 |

这张表有三点值得注意：

- 中性提示词下，单会话 5 次运行都没有调用子 Agent。也就是说，给了工具不等于模型会用。
- 提示词要求优先委派后，中位数已经接近 Super-agent（13.8 对 12.4），差距主要在最慢的那部分请求上（29.0 对 15.7）。
- Super-agent 快，是用 token 换的：按表里的数推算，读缓存的 token 约为中性提示词方案的 3.8 倍、优先委派方案的 2.1 倍。

**原型的现状**

配套仓库 [dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype) 以 MIT 协议开源，自己写明是研究原型，不是 DeepSeek 的正式产品，也不等同于内部版本，文章里的部分设计在原型里没有实现。目前它只接了 GitHub 和飞书两个来源。另外和文章略有不同：原型里开工前的确认消息由 Worker 自己写，结果和提问仍由 Router 发给人。

有两点和安全直接相关：

- **默认只记录不执行**。主动接受任务有三档：关闭、观察、自动，默认是观察。观察模式下，系统判断「该做」的事只会记下来，不会真的去做，文档建议先看过记录再切到自动。被授权的人明确提出的请求不受这个限制。
- **权限很大**。部署文档写明，Router 和 Worker 都以完全访问权限、用操作者本人的系统用户身份运行，Worker 执行命令不经审批，能读操作者的主目录。文档给的隔离建议是单独建一个只放 Agent 凭证的操作系统账户。

**文章列的未解决问题**

- 两层架构怎么扩展：Router 什么时候要拆分，Worker 之间要不要直连，跨月的长期记忆怎么做。
- 没有了「会话」这个界面，任务怎么呈现给人，人怎么中途介入。
- 安全和隐私：不可信输入、云端被攻破会波及所有接入的设备、凭证进入模型上下文的泄露风险。作者的原意是，这些不解决，系统就只能在很小且可信的范围里用。

**和以前有什么不同**

以前谈多 Agent 的好处，常说「并行更快」。这组初步实验更细：提示词写明优先委派后，单会话加子 Agent 的中位数已经接近，专门的调度层主要改善的是最慢的那批请求，读缓存的 token 约为 2.1 倍。它也没有回避主动型 Agent 的风险，原型里主动揽的活默认不自动执行。

**面试里怎么用**

被问「主动型 Agent 怎么设计」或「多 Agent 一定更快吗」时：

> 不一定。DeepSeek 的 Super-agent 文章里有一组初步实验：单会话配子 Agent 工具，如果提示词不强调，模型 5 次运行都没去委派；提示词写明优先委派后，完成时间的中位数就接近专门的 Router 加 Worker 架构了，差距主要在最慢的那部分请求。而 Router 架构读缓存的 token，按表推算约为这两种单会话方案的 2.1 倍和 3.8 倍。所以在这组合成负载上，和会委派的单会话比，专门的调度层买到的主要是稳定性，不是平均速度。主动性方面，它的开源原型对主动揽的活默认只记录本来会做什么而不执行，确认判断靠谱了再打开，这是主动型 Agent 上线的合理顺序。

**对应知识点**：[多智能体协作与适用边界](https://www.agent-journey.cn/knowledge?activeKey=multi-agent)、[Human-in-the-loop 审批与人工接管](https://www.agent-journey.cn/knowledge?activeKey=agent-human-in-loop)、[最小权限、授权与工具调用确认](https://www.agent-journey.cn/knowledge?activeKey=agent-permission-model)

想对照其他厂商的思路，可以看 [Harness 与长任务专题](https://www.agent-journey.cn/knowledge?activeKey=frontier-harness-long-running) 里 Anthropic 的「大脑和手分离」，以及 [多 Agent 与 Skill 专题](https://www.agent-journey.cn/knowledge?activeKey=frontier-multi-agent-skill) 里「什么时候该把子 Agent 收回主循环」。

## 练一练

### 高频考点题 1：Router 的职责

在 DeepSeek 的 Super-agent 设计里，Router 负责什么？

- A. 把一个大任务深入拆解成子任务，再逐个亲自执行完成
- B. 用最强的模型直接完成编码，做完后统一提交给人验收
- C. 定时检查其他会话有没有跑偏，发现异常就介入修复
- D. 承接所有和人的交互，在任务之间分派，自己不执行

**答案：D。** Router 是常驻的调度层，只做对人交互和任务之间的分派，不执行任务，可以用较轻的模型。深入拆解单个任务是团队负责人式主 Agent 的做法；执行工作由 Worker 承担；定时检查是 Watchdog 的职责。

### 高频考点题 2：实验说明了什么

文章的初步实验里，单会话加子 Agent 工具的方案在提示词要求优先委派后，完成时间的中位数接近 Super-agent。两者的主要差距在哪？

- A. Super-agent 读缓存的 token 更少，但最慢的那部分请求更慢
- B. Super-agent 最慢的那部分请求快得多，但读缓存的 token 更多
- C. 两者在最慢的请求上没有差距，只是读缓存的 token 不一样
- D. 单会话方案最慢的那部分请求更快，读缓存的 token 也更少

**答案：B。** 优先委派后中位数是 13.8 分钟对 12.4 分钟，差别不大；95 分位是 29.0 分钟对 15.7 分钟，差距明显。代价是 Super-agent 读缓存的 token 更多，所以它换来的主要是最慢请求的改善，而不是更省。

### 高频考点题 3：原型的默认行为

开源原型里，Agent 主动判断出「这件事该做」时，默认会怎样处理？

- A. 只记录下本来会做什么，不真的执行
- B. 立即执行并在群里通知所有人
- C. 先执行，再请人事后确认
- D. 直接丢弃这个判断，不留任何记录

**答案：A。** 原型的主动接受默认是观察模式，判断为该做的事只会被记录，方便操作者先检查判断质量，再决定是否切到自动模式。被授权的人明确提出的请求则会正常处理。
