有些工作需要读大量内容，却只需要留下一个很短的结论，比如“这个函数在哪些地方被调用”。把这类工作交给子任务，是控制上下文长度最有效的手段，也是研究模式能够并行的基础。

## 子任务是什么

子任务就是一个全新的执行循环：自己的系统提示词、自己的消息列表、自己的一组工具。主任务通过一个工具启动它，等它结束后只收到一段文字。

## 什么时候该派子任务

| 适合 | 不适合 |
|---|---|
| 探索性的查找：在大仓库里定位一段逻辑 | 修改代码：主任务看不到子任务改了什么 |
| 可以独立完成、互不依赖的多个问题 | 需要来回讨论的任务 |
| 过程冗长、结论简短的工作 | 两三步就能做完的小事 |

子任务有固定开销：它要从零开始理解任务，系统提示词和工具定义也要重新计一次费。小任务派出去反而更慢更贵。在“派发子任务”这个工具的说明里把上表写清楚，模型才会用对。

## 任务说明要写完整

子任务看不到主任务的任何对话。主任务里说了半天的背景，子任务一无所知。所以任务说明必须自己就能读懂，至少包含：

- 要回答的问题或要完成的目标。
- 已经知道的信息和已经排除的方向。
- 希望以什么形式返回结果。

在工具说明里明确告诉模型这一点，并给一个对比：

```text
差：找一下那个报错的地方

好：在 shop/ 目录下找出所有调用 calculate_discount() 的位置。
    已知它定义在 shop/pricing.py 第 42 行。
    请返回一个列表，每项包含文件路径、行号和所在函数名。不需要修改任何文件。
```

## 调度器的职责

```python
class SubagentScheduler:
    def __init__(self, max_parallel: int = 3, max_depth: int = 1): ...

    async def spawn(self, task: str, toolset: str, parent_depth: int) -> str:
        if parent_depth >= self.max_depth:
            return "子任务不能再派发子任务。请直接完成这项工作。"
        async with self._semaphore:
            loop = AgentLoop(
                system=prompts.subagent(toolset),
                tools=registry.subset(toolset),
                permission=self.permission,      # 与主任务共用同一个闸门
                max_turns=30,
            )
            return await loop.run(task)
```

四个设计决定：

1. **限制嵌套深度。** 默认子任务不能再派子任务。否则一个判断失误就会变成指数级的调用。
2. **限制并行数。** 用信号量控制同时运行的子任务数量，默认 3 个。并行数受模型接口的限流和你的预算约束。
3. **限制工具集。** 探索类的子任务只给只读工具。它不能改文件，自然也不需要弹确认。
4. **共用权限闸门。** 子任务的每次工具调用同样要过闸门，没有例外。这是架构一章的第二条约束。

## 并行

模型在一次回复里发出多个“派发子任务”调用时，调度器让它们同时运行：

```python
results = await asyncio.gather(
    *(scheduler.spawn(c.arguments["task"], "explore", depth) for c in calls),
    return_exceptions=True,
)
```

`return_exceptions=True` 保证一个子任务失败不会拖垮其他的。失败的那一个把错误说明作为结果返回，由主任务决定是重试、换个问法还是放弃这一路。

并行带来的两个问题要提前想好：

- **重复劳动。** 两个子任务可能查到同一批资料。派发前让主任务把子问题切得互不重叠，是成本最低的解决办法。
- **进度展示。** 三个子任务同时输出会搅在一起。终端里只为每个子任务显示一行当前状态，详细过程写进各自的会话文件。

## 结果怎么交回

子任务的最后一条回复就是交给主任务的全部内容。在子任务的系统提示词里约定格式：

- 先给结论，再给依据。
- 引用文件时带路径和行号，引用网页时带来源编号。
- 没找到就明确说没找到，并说明找过哪些地方。

最后一条很关键。子任务如果在没找到时编一个看似合理的答案，主任务没有任何办法分辨。

主任务不应该无条件相信子任务的结论。在主任务的提示词里提醒：子任务给出的位置，在据此修改之前要自己读一遍确认。

## 子任务和多智能体的关系

面试里经常把两者放在一起问。可以这样区分：

| | 子任务 | 多个对等的智能体 |
|---|---|---|
| 关系 | 主从：一个主管派活，其他只管干 | 对等：互相发消息、协商 |
| 上下文 | 各自独立，单向汇报 | 需要共享状态或消息通道 |
| 复杂度 | 低，就是一次带返回值的调用 | 高，要处理通信、冲突、死锁 |
| 适用 | 能拆成独立子问题的任务 | 需要不同角色反复交互的任务 |

本项目只做主从结构。它覆盖了多智能体最主要的收益，即上下文隔离和并行，而实现和调试的难度低得多。下一章的研究模式就是这个结构的直接应用。

## 自己动手时的检查点

1. 在一个中等规模的开源仓库里问一个需要全局查找的问题，对比派子任务和不派子任务时主任务的上下文用量。
2. 同时派出三个子任务，让其中一个必定失败，确认另外两个的结果正常返回。
3. 在子任务里诱导它再派子任务，确认被拒绝。
4. 给一个含糊的任务说明，观察子任务的结果有多差；再改成完整的说明对比。

## 面试常见追问

- **为什么要用子任务？** 上下文隔离和并行两点，用具体数字说明主任务窗口省了多少。
- **子任务失败了怎么办？** 错误作为结果返回，主任务决定重试或降级；并行时互不影响。
- **怎么控制成本？** 嵌套深度、并行数、每个子任务的轮次上限三个闸。
- **什么时候不该用多智能体？** 任务小、步骤间强依赖、需要共享大量上下文时。
