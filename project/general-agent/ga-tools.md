工具决定 Agent 能做什么，工具的说明文字决定模型会不会用对。这一章讲工具注册表的设计，以及编程模式六个基础工具各自的取舍。

## 工具注册表

注册表是内核和具体工具之间唯一的接口，只暴露三个方法：

```python
class ToolRegistry:
    def register(self, tool: Tool) -> None: ...
    def schemas(self) -> list[dict]: ...          # 发给模型的工具定义
    async def execute(self, call: ToolCall) -> str: ...
```

`execute` 内部按固定顺序做四件事：

![工具注册表 execute 的固定顺序：收到工具调用后先看工具是否存在，不存在就返回没有这个工具以及可用的有哪些；再看参数是否符合格式，不符合就返回哪个参数错了、期望什么；然后带超时执行，抛异常就返回异常类型和信息；最后看结果是否过长，过长就截断并说明如何取剩余部分，否则原样返回](https://font-end-journey-resources.oss-cn-hangzhou.aliyuncs.com/images/project-ga-tools-execute-four-checks-v1.dark.png)

*下面一排红框都是返回给模型的内容：出错不抛给用户，而是告诉模型错在哪。*

四个出口返回的都是字符串。注册表永远不向上抛异常，这样执行循环不需要关心任何一个工具的内部细节。

用装饰器注册，函数签名和文档字符串直接生成工具定义：

```python
@tool(read_only=True)
async def read_file(path: str, offset: int = 0, limit: int = 2000) -> str:
    """读取文本文件的内容，返回带行号的文本。

    文件较大时用 offset 和 limit 分段读取。修改文件之前必须先读取它。

    Args:
        path: 相对于工作目录的文件路径
        offset: 从第几行开始，0 表示开头
        limit: 最多读取多少行
    """
```

## 六个基础工具

| 工具 | 只读 | 作用 | 关键设计 |
|---|---|---|---|
| 读文件 | 是 | 返回带行号的文件内容 | 分段读取；记录“已读”状态供改文件时校验 |
| 写文件 | 否 | 创建或整体覆盖一个文件 | 覆盖已有文件前要求先读过 |
| 改文件 | 否 | 把文件里的一段文字替换成另一段 | 被替换的文字必须在文件里唯一出现 |
| 执行命令 | 否 | 在工作目录里跑一条命令 | 超时、输出截断、危险命令拦截 |
| 按名查找 | 是 | 按通配符找文件 | 默认忽略依赖目录和构建产物 |
| 按内容搜索 | 是 | 在文件内容里搜正则 | 限制返回条数，附带行号 |

### 为什么改文件用“替换一段文字”

让模型修改文件有三种常见做法，各有问题：

| 做法 | 问题 |
|---|---|
| 让模型输出完整的新文件 | 文件一长就又慢又贵，还容易悄悄漏掉中间的内容 |
| 让模型给出行号范围 | 模型数行号经常数错，前一次修改后行号也会变 |
| 让模型给出原文片段和新片段 | 片段必须和原文逐字符一致，否则替换失败 |

第三种失败时是明确报错，前两种失败时是悄悄改坏，所以选第三种。实现时加两条规则让它更稳：

- 原文片段在文件里出现多次时拒绝执行，并告诉模型出现了几次，要求它多带几行上下文。
- 修改前校验文件自上次读取后有没有被别的程序改过。变了就要求重新读取。

### 执行命令是最危险的工具

这个工具需要四项基本处理，全部在工具内部完成，不依赖模型自觉：

1. **超时**。默认 120 秒，超时后杀掉整个进程组，返回已有的输出。
2. **输出截断**。保留开头和结尾各一部分，中间用一行说明省略了多少。测试失败的关键信息通常在结尾。
3. **固定工作目录**。命令一律从项目目录启动。这只是固定了起点，命令字符串里仍然可以写出项目之外的路径，工具自己拦不住，边界要靠下一章的权限闸门和沙箱。
4. **不提供交互**。需要键盘输入的命令会卡住，所以标准输入直接关闭，并在工具说明里告诉模型加上免交互的参数。

哪些命令需要用户确认不由这个工具决定，那是下一章权限闸门的事。

## 工具说明怎么写

工具的 `description` 是写给模型看的使用说明，它对效果的影响经常超过系统提示词。写的时候回答四个问题：

1. 这个工具做什么。
2. 什么时候该用它，什么时候该用别的工具。
3. 参数的含义和格式，给一个例子。
4. 结果是什么样子，出错时会返回什么。

对比两种写法：

```text
差：搜索文件内容。

好：在文件内容里搜索正则表达式，返回匹配行及其文件路径和行号。
    想找某个函数、变量、报错信息在哪里时用它；只知道文件名时用“按名查找”。
    最多返回 100 条，超出时会提示缩小范围。
    例：pattern="def calculate_.*", path="shop/"
```

## 工具结果怎么写

工具返回的文字也是写给模型看的。三条经验：

- **带上定位信息**。读文件带行号，搜索结果带路径和行号，模型下一步才能精确引用。
- **截断时说明白**。写清楚截掉了多少、怎样拿到剩下的部分。只截断不说明，模型会当成内容就这么多。
- **空结果要给出下一步**。没搜到时提示可能的原因，比如大小写、路径范围。

## 研究模式的工具

研究模式的三个工具（联网搜索、读网页正文、压缩摘录）遵循同样的注册方式，放在研究模式一章讲。这里只强调一点：对内核来说它们和读文件没有区别，都是一个名字、一份参数格式、一个执行器。

## 自己动手时的检查点

1. 故意让模型调用一个不存在的工具名，确认它收到可用工具列表后能自己纠正。
2. 让它修改一个出现了两处相同代码的文件，确认工具拒绝并要求更多上下文。
3. 让它执行 `sleep 300`，确认到时间能被杀掉并返回说明。
4. 让它读一个上万行的文件，确认是分段读取而不是一次塞进上下文。

## 面试常见追问

- **工具多了模型选不准怎么办？** 先改说明文字，写清楚各工具的分工；再减少同时暴露的数量，按模式和技能按需加载。
- **模型给的参数不合格式怎么办？** 注册表做校验，把哪个参数错了、期望什么写回去，让模型重试。
- **怎么防止模型改坏文件？** 唯一匹配、先读后改、修改前校验文件是否变化，加上权限闸门的确认。
