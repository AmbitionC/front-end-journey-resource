“通过率 72%”这句话漏掉了大部分信息：同一条任务再跑一次还能过吗，这 72% 花了多少钱，比上一版的 68% 真的更好吗。这一章把单个通过率扩展成一份能支持决策的报告。

本章的思路参考 Princeton 等机构 2026 年 10 月的《Emerging Trends in AI Agent Evaluation》，该文梳理了 Agent 评测从只报准确率转向同时报告可靠性和成本的趋势。

## 同一条任务要跑多次

模型输出有随机性。一条任务跑 5 次，可能过 3 次。只跑一次时，你看到的是通过还是失败纯属运气。

每条任务跑 k 次之后，可以算出两个含义完全不同的数：

| 指标 | 定义 | 回答的问题 |
|---|---|---|
| 至少成功一次 | k 次里有任意一次通过的任务占比 | 这件事它有没有能力做到 |
| 每次都成功 | k 次全部通过的任务占比 | 这件事能不能放心交给它 |

```python
def reliability(runs: dict[str, list[bool]]) -> dict:
    n = len(runs)
    return {
        "pass_any": sum(any(r) for r in runs.values()) / n,
        "pass_all": sum(all(r) for r in runs.values()) / n,
        "mean":     sum(sum(r) / len(r) for r in runs.values()) / n,
    }
```

两个数之间的差距就是不稳定的部分。差距很大时，改进的重点是稳定性而不是能力。对用户来说，一个十次里错三次的助手和一个不会做的助手差别不大。

k 取多少取决于预算。本项目默认 5 次，这是在成本和稳定之间取的起步值。

## 把不稳定的任务找出来

```python
flaky = [t for t, r in runs.items() if 0 < sum(r) < len(r)]
```

逐条看这些任务的轨迹，通常是三种原因之一：

| 原因 | 表现 | 处理 |
|---|---|---|
| 任务有歧义 | 不同运行对任务的理解不同 | 改任务描述 |
| 评分不稳定 | 相同的结果有时判过有时判不过 | 修评分器 |
| Agent 行为不稳定 | 有时验证有时不验证 | 这才是该用进化去解决的问题 |

前两种是评测自身的问题，要先修掉，否则会污染后面所有结论。

## 成本必须和通过率一起报

多跑几轮、多派几个子任务、换更贵的模型，通常都能涨分。不看成本的通过率对比没有意义。

把每个版本的花费和通过率并排列出来（数字为示意）：

| 版本 | 平均每条花费 | 平均通过率 | 结论 |
|---|---|---|---|
| v12 | ¥0.19 | 68% | 被 v15 淘汰：v15 更便宜也更好 |
| v13 | ¥0.21 | 75% | 在前沿上 |
| v14 | ¥0.45 | 77% | 在前沿上，但比 v13 贵一倍只高一点 |
| v15 | ¥0.17 | 71% | 在前沿上，最便宜 |

读法：如果存在另一个版本又便宜又好，这个版本就被淘汰。没有被任何版本同时在两个维度上超过的那些，构成可选的前沿。前沿上选哪个取决于你的场景：v14 是否值得多花一倍的钱，评测本身回答不了。把这张表画成散点图（横轴花费、纵轴通过率）更直观。

同时记录的还有耗时和轮次。对交互式的 Agent，耗时本身就是体验的一部分。

## 两个版本的差距是真的吗

40 条任务上，68% 和 72% 只差不到 2 条任务。判断这个差距是否可信，用三个由简到繁的办法。

**逐条对比。** 把两个版本在每条任务上的通过次数并排列出来：

| 任务 | v12 通过次数 | v13 通过次数 | 变化 |
|---|---|---|---|
| cart-rounding | 2/5 | 5/5 | 变好 |
| auth-expiry | 5/5 | 3/5 | 变差 |
| …… | | | |

总分上涨而有任务明显变差时，要先弄清楚变差的原因。

**同一版本自己和自己比。** 把同一个版本完整跑两遍，两遍的通过率之差就是纯随机波动的大小。新版本带来的提升如果没有明显超过这个差值，就不能下结论。这个办法不需要统计知识，而且非常直观。

**配对的重采样。** 想要一个更正式的判断时，对任务做有放回的重采样：

```python
def paired_bootstrap(a: dict, b: dict, n_boot: int = 10000, seed: int = 0) -> float:
    """返回“b 的平均通过率高于 a”在重采样中出现的比例。"""
    rng = random.Random(seed)
    tasks = list(a)
    wins = 0
    for _ in range(n_boot):
        sample = [rng.choice(tasks) for _ in tasks]
        diff = sum(mean(b[t]) - mean(a[t]) for t in sample)
        wins += diff > 0
    return wins / n_boot
```

这个比例接近 1 时，差距比较可信；在一半附近时，两者没有可分辨的差别。任务数很少时这个估计本身也粗糙，它是辅助判断，不是裁决。

## 报告长什么样

每次评测输出一份固定结构的报告：

```text
版本 v13（父版本 v12）  评分器 coding-grader@3  每条任务 5 次

                 v12      v13
至少成功一次     85.0%    87.5%
每次都成功       50.0%    62.5%
平均通过率       68.0%    74.5%
平均花费         ¥0.19    ¥0.21
平均耗时         71s      74s

变好的任务 6 条   变差的任务 1 条   不稳定任务 10 条
同版本重复运行的波动：±3.5%
停止原因：正常结束 88%  轮次上限 9%  超时 3%
```

以上数字为格式示意。

最后两行不要省。波动范围告诉读报告的人这次提升能不能信，停止原因的分布常常直接指出问题所在。

## 自己动手时的检查点

1. 把当前版本每条任务跑 5 次，算出“至少成功一次”和“每次都成功”，看差距有多大。
2. 把不稳定任务逐条归到三种原因里，修掉属于任务和评分器的那些。
3. 同一个版本完整跑两遍，记下通过率的差值。
4. 画出你已有几个版本的花费与通过率散点图。

## 面试常见追问

- **只看准确率够吗？** 讲两个可靠性指标的区别，以及成本和耗时为什么必须一起报。
- **结果有波动怎么办？** 多次运行、同版本自比得到波动范围、逐条对比。
- **怎么证明一次改进有效？** 提升要超过波动范围；没有任务明显变差；成本没有不成比例地上涨。
- **评测太贵怎么办？** 先在小子集上筛，只对有希望的候选跑完整评测；缓存没有变化的部分。
