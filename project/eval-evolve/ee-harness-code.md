最后一级不再限定“可以改什么”。提案器直接修改 Agent 外壳的源代码：换一种压缩策略、加一个新工具、重写子任务的调度方式。这一级是选做，它的成本和风险都明显高于前三级。

本章的思路来自 2026 年 3 月的论文《Meta-Harness: End-to-End Optimization of Model Harnesses》。

## 论文的做法

论文的方法可以概括成四点：

| 要点 | 内容 |
|---|---|
| 提案器是一个编程 Agent | 论文使用的是一个现成的编程 Agent，配一份很短的说明文件 |
| 历史全部放在文件系统里 | 每个历史版本的源代码、得分和执行轨迹都落盘，提案器自己用查找和读文件的命令去翻 |
| 不压缩反馈 | 不把历史总结成摘要再喂给提案器，而是让它按需读原始内容 |
| 保留一组版本 | 每轮提出若干个新外壳，评测后记入历史，保留前沿上的多个版本，不规定必须从哪个版本改起 |

论文里外壳是一个单文件的 Python 程序，底层模型固定不变，一次典型的搜索大约评测 60 个外壳、迭代 20 轮。

论文的消融实验给出了一个对工程实现很有指导意义的结果：提案器只能看到分数时，效果明显不如能看到完整执行轨迹时。这和 GEPA 的结论方向一致：反馈的信息量决定了优化能走多远。

论文公开了官方代码，其中包含搜索框架，也有它在 Terminal-Bench 2 上优化得到的外壳成品。本章没有直接使用它，而是按上面四点自己实现一个小规模版本，原版可以作为对照来读。

## 本项目的特别之处

论文里的提案器是一个现成的编程 Agent。而你在第一个项目里已经写了一个编程 Agent。

所以这一章的设置是：**用你自己写的编程 Agent 当提案器，去改它自己的外壳代码。** 它读自己的源码、自己过去的失败轨迹，写出自己的下一个版本。能不能做出明显的效果不一定，但这个设置本身就是一个很好的面试话题，前提是你把下面的安全边界做扎实。

## 历史目录

提案器的全部信息来源是一个只读目录：

```text
history/
  README.md                  目录结构说明，以及提案器要遵守的接口约定
  versions/
    v017/
      harness/               这个版本的外壳源码
      scores.json            进化集上每条任务的得分、花费、轮次
      traces/                进化集上每次运行的完整轨迹
      note.md                这个版本想解决什么，结果如何
    v018/
      ……
  rejected/
    c031/                    被拒绝的候选，同样的结构，外加拒绝原因
  frontier.json              当前前沿上有哪些版本
```

三点要注意：

- 目录里只有进化集的数据。验收集和回归集的任务、轨迹、得分都不在里面。
- 被拒绝的候选也保留。提案器能看到“这条路走过，不通”。
- 不预先生成摘要。提案器想知道某个版本为什么在某条任务上失败，就自己去读那条轨迹。

## 提案器的任务说明

```text
你的任务是改进 harness/ 目录下的 Agent 外壳代码。

history/ 目录是只读的，里面有历史版本的源码、它们在一组任务上的得分和完整轨迹，
以及被拒绝的候选和拒绝原因。先阅读 history/README.md。

工作方式：
1. 浏览 frontier.json 和各版本的 scores.json，找出表现差或不稳定的任务。
2. 阅读这些任务的轨迹，弄清楚外壳的哪部分行为导致了失败。
3. 选一个历史版本作为起点，把它的 harness/ 复制到工作目录后修改。
4. 运行 make check，确认接口检查和冒烟测试通过。
5. 写一份 note.md：改了什么、为什么、预期影响哪些任务、可能的风险。

约束：
- 不要修改 kernel/permission.py 和 evals/ 下的任何文件。
- 不要针对具体任务写特殊处理。修改必须是通用的。
- 一次只做一个主题的修改。
```

这份说明刻意写得很短。论文的做法同样是给提案器一份最小化的指引，把怎样诊断、从哪里改起的决定权留给它。

*图：虚线框里是沙箱。提案器对历史目录只能读；候选的评测结果由沙箱外的控制器写回历史。*

每轮可以并行启动几个提案器，各自独立工作，得到几个不同方向的候选。

搜索过程中的评测只用进化集。搜索结束后，从前沿上取出最好的几个版本，交给准入闸门，在验收集和回归集上各评测一次。提案器自始至终看不到这两套任务的结果。论文也是同样的安排：提案器不接触测试集，最终评测只对前沿上的版本做一次。

## 安全边界

让一个 Agent 改写自己的代码，必须把它关在明确的边界里。

| 边界 | 做法 |
|---|---|
| 提案器在沙箱里运行 | 容器，无外网，只能写自己的工作目录 |
| 候选代码在沙箱里运行 | 评测一个由模型写出的外壳，等于执行不可信代码，隔离级别和提案器相同 |
| 改动范围检查 | 权限闸门和评测相关的文件有任何改动，直接拒绝 |
| 接口检查 | 候选必须实现接入约定里的接口，并通过一组冒烟测试 |
| 人工复核 | 进入准入闸门之前，人读一遍代码差异和 note.md |
| 不自动上线 | 通过闸门的版本进入版本库，是否成为日常使用的版本由人决定 |

第二条容易被忽略。前三级改的是文字和配置，候选版本运行的还是你写的代码。这一级候选版本运行的是模型写的代码。

静态检查还要防一类针对评测的作弊：候选代码里出现任务编号、测试文件名、特定输入的字符串时拒绝。这是审计一章“写死答案”的代码版本。

## 成本控制

这是四级里最贵的一级：每个候选都要提案器工作一次，再完整评测一次。

- **缩小搜索集。** 搜索阶段只用进化集里区分度高的一个子集，即那些不同版本表现不一样的任务。所有版本都能过或都过不了的任务，对比较版本没有帮助。
- **分级评测。** 候选先跑冒烟测试，再跑小子集，表现不差于起点的才跑完整的进化集。
- **限定轮数。** 本项目建议从 3 到 5 轮、每轮 2 个候选起步。这比论文的规模小一个数量级，目的是把流程跑通并观察现象。

动手之前先估算花费：每个候选的评测次数乘以单次平均花费，再乘以候选数。数字超出预算就继续缩小。

## 对结果保持诚实

这一章有三种可能的结果，都可以写成结论：

1. **找到了有效的代码修改。** 记录它是什么、提案器是从哪些轨迹里发现问题的、验收集上的提升有没有超出波动范围。
2. **进化集上涨了，验收集上没涨。** 这是过拟合的直接证据，本身就是下一章要讨论的现象。
3. **没有找到任何提升。** 分析原因：提案器的能力不够、任务集太小没有信号、还是前三级已经把容易修的问题修完了。

论文自己也列出了它的局限，例如在一个基准上搜索和评测用的是同一批任务，以及只研究了一种提案器。读论文时把局限部分和结果部分一起读。

## 自己动手时的检查点

1. 建好历史目录，确认里面没有验收集和回归集的任何内容。
2. 让你的编程 Agent 作为提案器跑一轮，读它写的 note.md，判断它的诊断是否基于轨迹里的事实。
3. 让提案器尝试修改权限闸门，确认候选被静态检查拒绝。
4. 把提案器能看的信息削减到只有分数，对比它提出的修改质量。

## 面试常见追问

- **Agent 能改自己的代码吗？** 能，讲历史目录、提案器、评测、前沿四个部件。
- **怎么保证它不把自己改坏？** 沙箱、改动范围检查、提案器看不到验收数据、人工复核、不自动上线。
- **为什么给完整轨迹而不是摘要？** 引用论文的消融结果，再讲你自己的对比。
- **这一级和前三级的本质区别？** 搜索空间从文字和有限的配置扩大到任意代码，候选本身变成不可信代码。
