评测与自进化平台的代码量最小，但对「对不对」的要求最高：一把量不准的尺子，后面所有的进化结论都不可信。

这一章不讲新的设计，讲的是做法：把前面各章的内容交给 Claude Code、Cursor 这类 AI 编程工具，一步一步做出一个能通过测试的版本。源码包的 `build-with-ai/` 目录里有配套的三份材料：需求文档、任务清单、提示词。

先说清楚这是什么性质的练习。测试是照着配套源码的接口写的，所以你做出来的东西在模块划分上会和源码接近。这是带着答案做题，价值在于过程：工具第一版哪里写错了、你是怎么发现的、最后为什么这样改。这些只有自己做过才讲得出来。

## 为什么不能一句话让它全写完

把整份需求丢给工具说「帮我实现」，它会写出几千行看起来完整的代码。问题有三个：

- **你读不过来。** 一次生成的代码超过你能认真读完的量，剩下的就只能相信它。面试时被问到任何一处细节，你都答不上来。
- **错误会叠在一起。** 底层的一个接口定错了，上面十个文件都跟着错。等测试暴露出来，已经分不清是哪一层的问题。
- **它会替你做决定。** 需求里没说清的地方，它会选一个看起来合理的做法，而且不会告诉你它选过。

所以整个过程围绕一件事组织：每一步都小到你能读完、能验收。

## 三份材料各管什么

| 文件 | 回答的问题 | 写的时候最容易漏的 |
|---|---|---|
| 需求文档 `requirements.md` | 做成什么样算完成 | 「明确不做」和「必须由代码保证」 |
| 任务清单 `tasks.md` | 先做什么后做什么，每一步怎么验收 | 每个里程碑的验收命令 |
| 项目说明文件（`AGENTS.md` 或 `CLAUDE.md`） | 在这个项目里干活要守哪些规矩 | 不许改测试、一次只做一个里程碑 |

「明确不做」这一节的作用比看上去大。工具倾向于多做：加配置项、加抽象层、加「以后可能用到」的参数。不写清楚边界，它每一步都会多带一点东西进来。

「必须由代码保证」这一节是这个项目特有的，也是后面做检查的依据。这个项目里有五条：提案器拿不到验收集和回归集的信息、外壳配置的修改必须在允许范围内、外壳代码先过静态检查和试跑、经验手册只许增量修改、没过闸门的候选不会成为当前版本。

## 准备工作

1. 新建一个空目录。不要在源码包上直接改，那样做出来的只是一份改过的源码。
2. 把源码包的 `tests/`、`tasks/` 复制过去。网站在线试用接入的那个测试文件不要复制。这个项目安装时依赖通用 Agent 的源码，新目录里要用 `pip install -e <通用 Agent 的路径> -e ".[dev]"`。
3. 把 `build-with-ai/prompts.md` 里的项目说明文件存到根目录，`requirements.md` 和 `tasks.md` 也放进去。
4. 开工前先让工具只读不写：读完需求和任务清单，说出系统有哪几个部件、最容易做错的三个地方。它说得不对的地方，就是需求文档没写清楚的地方，先改文档。

## 里程碑怎么排

顺序是先尺子、后进化。任务集、评分器、运行器、审计都验收过之后，才开始写提案器和闸门。闸门排在提案器前面，因为四级提案器都要过同一道闸门，先把它做对。

| 里程碑 | 做什么 | 验收 |
|---|---|---|
| 0 | 骨架 | 所有测试文件能被导入 |
| 1 | 任务集和评分器 | 划分和评分器相关的几条 |
| 2 | 运行器、结果库和报告 | 评分、报告、存储测试 |
| 3 | 评分器审计 | 审计测试，加对自带任务跑一次审计 |
| 4 | 接入被测 Agent | 适配器和外壳配置测试 |
| 5 | 准入闸门 | 进化测试里和闸门相关的几条 |
| 6 | 四级提案器 | 进化测试全部通过 |
| 7 | 命令行 | 全部测试 |

里程碑 0 只建骨架：所有模块的文件都在，类和函数先留空。需要这一步是因为测试文件在开头就把模块全部导入了，没有骨架，每个里程碑的验收命令都会卡在导入错误上。

任务清单里每个里程碑还有一栏「容易出错的地方」。先不要告诉工具，等它做完再对照，看它踩没踩到。踩到了，这就是一个现成的迭代故事。

## 每个里程碑的四步

**先要计划。** 让它读这个里程碑对应的测试，给出要新建哪些文件、每个文件的职责、关键的函数签名。用 Claude Code 可以直接进计划模式，这样它想提前动手也动不了。计划里出现了任务清单范围之外的东西，这时候删掉最便宜。

**再让它实现。** 只做这个里程碑，写完自己跑验收命令。测试不过就修实现。

**然后自己读。** 把它写的代码从头读一遍，再打开源码里对应的文件对照。不一样的地方分三类记下来：它的写法更好、源码的写法更好、只是风格不同。前两类都值得弄明白原因。

**最后换一个会话做检查。** 不要在写代码的那个会话里问「你写得对吗」，它会倾向于说对。新开一个会话，让它扮演没参与实现的审查者，逐条回答需求文档里「必须由代码保证」的每一条是在哪一行代码里保证的。这一步在这个项目里尤其有用：

- 提案器看不到验收集：检查传给提案器的数据里有没有验收集和回归集的任务编号或结果。
- 外壳配置的取值范围：检查越界的修改是在评测之前就被拒绝，还是跑完才发现。
- 没过闸门的候选不会成为当前版本：检查「设为当前版本」是不是只有闸门一处能调用。

## 这个项目最容易写错的地方

下面几处是源码和测试专门防过的，工具的第一版很可能踩到其中一两处。做完每个里程碑对照着查一遍。

- **评分器只看退出码。** 把测试文件删了，检查命令照样返回成功。审计一章讲的几种作弊，对照着逐种检查。
- **只报平均通过率。** 「至少成功一次」和「每次都成功」没有分开。
- **相似任务跨了集合。** 同一个缺陷的两个变体，一条在进化集、一条在验收集，等于提前看了答案。
- **回归把基线本来就不过的任务也算上。** 结果是任何候选都被判退步，或者任何候选都不算退步。

还有一类问题和具体项目无关：一条测试连续修了几次都没过，它开始在实现里打补丁，甚至想去改测试。这时候让它停下来，把测试的断言、相关的实现、实际的输出各贴一遍，再说出它对「这条测试到底在要求什么」的理解。多数时候是理解错了，继续改实现只会越改越远。

## 做完之后手里有什么

- 一份自己做出来、能通过同一套测试的代码，和每个里程碑的提交记录。
- 一份对照笔记：每个里程碑里工具哪里做错了、你怎么发现的、和源码的差异。
- 至少一处你自己的改动，例如把教程里某条「留作练习」做掉，或者补几条测试。

写进简历时，按「面试准备」里的口径如实写：参考了公开的教程和源码，用 AI 编程工具按里程碑实现，自己做了哪些改动、发现过哪些问题。不要写成没有参考、全部由自己设计。

## 面试常见追问

- **这个项目是 AI 写的吧，你做了什么？** 讲你怎么拆里程碑、怎么验收、读代码时发现过什么问题，举一个具体的例子。
- **你怎么保证 AI 写的代码是对的？** 测试先行、每步验收、换会话审查关键约束、和参考实现对照。
- **用 AI 编程工具最大的坑是什么？** 讲一次生成太多读不过来，以及需求没说清时它会悄悄替你做决定。
- **不用 AI 你能写出来吗？** 照实答。能讲清每个部件为什么这样设计、能指出工具写错的地方，比能不能默写更有说服力。
