前面四章都在讲怎样让 Agent 变好。这一章讲它的反面：进化会带来什么问题，以及那道一直被提到的准入闸门具体怎么实现。

本章对应两篇 2026 年 10 月的论文：《Are Self-Evolving Agents Continual Learners?》和《Self-Evolving Agent Harness》。

## 学新的，忘旧的

第一篇论文研究的问题是：自进化的 Agent 在任务类型不断变化的情况下表现如何。它把任务排成一条随时间变化的序列，先是一类任务，再换成另一类，对比了三种方法：检索记忆条目的 ReasoningBank、改写系统提示词中策略部分的 GEPA、可以修改提示词、记忆、技能文件和控制代码的 Meta-Harness。模型权重全程不变。

论文摘要给出的结论是：自进化在多数序列上提升了总体表现，但更高的可塑性始终以稳定性为代价。能修改自身的方法会因为全局性的修改而互相干扰；基于相似度的检索也仍然会取回不属于当前任务类型的记忆。

两个概念：

| | 含义 | 太低的后果 |
|---|---|---|
| 可塑性 | 遇到新类型任务时能学会多少 | 学不会新东西 |
| 稳定性 | 学了新东西之后旧任务还保持多少 | 学一样丢一样 |

用白话说：一个方法能改的东西越多，越容易在改好新任务的同时改坏旧任务。提示词里为新任务加的一句话，对旧任务可能是误导。这正是本项目从第一章起就设置回归集的原因。

从这张表可以读出两个量，定义参照论文里的度量方式：

- **学到了多少**：每一类任务在刚学完它的那一刻，相对初始版本的提升。
- **忘了多少**：每一类任务从刚学完时到全部结束时，得分下降了多少。

```python
def plasticity(A: dict, baseline: dict, learned_at: dict) -> float:
    return mean(A[learned_at[k]][k] - baseline[k] for k in learned_at)

def forgetting(A: dict, learned_at: dict, final: str) -> float:
    return mean(max(0.0, A[learned_at[k]][k] - A[final][k]) for k in learned_at)
```

对四个级别分别做这个实验，放在一起比较。按论文的结论，你有可能看到级别越高遗忘越明显，但在你的任务集上不一定如此。看到什么就写什么。

这个实验在做的时候要关掉回归集检查，目的就是观察没有保护时会发生什么。然后打开回归检查再做一遍，对比遗忘量的变化，这就是闸门价值的直接证据。

## 准入闸门

第二篇论文是一篇理论和框架性质的工作。按摘要的描述，它把“被接受的修改会跨运行保留下来”这件事形式化，区分了修改的对象、提案的机制和准入的机制，并给出了一个结论方向：准入规则应当使用新的、独立的验证数据，同时在有限的回归预算下约束对旧能力的保持。摘要同时强调，可靠的部署需要持续验证和独立的保障措施。

我们没有实现论文里的理论推导，只取它的工程含义，落成四条规则。

### 规则一：验收数据独立于提案过程

提案器看不到验收集，这一点各章已经反复强调。这里补上时间维度的问题。

每一次准入判定都会泄露一点验收集的信息：通过的留下，没通过的淘汰。几十次判定之后，留下来的版本整体上已经被验收集筛选过，它在验收集上的分数会高于在全新任务上的分数。论文说的“新的”验证数据，针对的就是这一点。

工程上的做法：

```python
class AcceptancePool:
    def draw(self, k: int) -> list[Task]:
        """每次准入从池中抽取 k 条，优先抽使用次数少的。"""
        ranked = sorted(self.tasks, key=lambda t: (self.uses[t.id], self.rng.random()))
        chosen = ranked[:k]
        for t in chosen:
            self.uses[t.id] += 1
        return chosen

    def retire(self, max_uses: int) -> list[Task]:
        """用过太多次的任务退役到进化集，并提醒需要补充新任务。"""
```

使用次数上限是本项目自己定的工程参数。它没有理论保证，作用是提醒你验收集需要持续补充新任务。

### 规则二：提升要超过波动

可靠性一章已经测过同一版本重复运行的波动范围。准入时要求候选在验收集上的提升大于这个范围，否则视为没有提升。

对一个长期运行的进化过程，这条规则很关键。每次准入都有一定概率放进一个其实没有变好的版本，判定的次数越多，累计放进来的无效修改越多。把门槛定在波动范围之上，是控制这个累计错误最简单的办法。

### 规则三：回归集不退步

```python
def regression_ok(candidate: Scores, baseline: Scores, budget: int = 0) -> tuple[bool, list[str]]:
    regressed = [t for t in baseline
                 if baseline[t].pass_all and not candidate[t].pass_all]
    return len(regressed) <= budget, regressed
```

回归集里是基线版本每次都能通过的任务。候选版本在其中任何一条上不再每次通过，就算退步。

`budget` 是允许退步的条数，默认为 0。有时一个很有价值的修改会让一条不重要的旧任务退步，可以由人决定放宽，但这必须是一个显式的、被记录下来的决定。

### 规则四：成本不能失控

通过率上升但平均花费或耗时超过设定的倍数时，不自动合入，交给人判断。本项目的默认上限是基线的 1.3 倍。

### 合在一起

```python
async def admit(candidate: AgentVersion, baseline: AgentVersion) -> Decision:
    accept_tasks = pool.draw(k=ACCEPT_K)
    cand, base = await evaluate_both(candidate, baseline, accept_tasks, repeat=5)

    if cand.mean - base.mean <= noise_band(base):
        return Decision.reject("提升未超过波动范围")

    ok, regressed = regression_ok(await evaluate(candidate, REGRESS_SET, repeat=5), regress_baseline)
    if not ok:
        return Decision.reject(f"回归集退步：{regressed}")

    if cand.cost > base.cost * COST_CAP:
        return Decision.needs_human("成本超过上限")

    return Decision.accept(flipped=newly_passing(cand, base))   # 交人工复核
```

通过之后，从失败变为通过的那几条任务进入人工复核队列，这是评分器一章定下的规矩。

### 配套源码里的闸门

上面是完整的设计。配套源码为了拿到手就能跑，实现的是一个简化版，判定顺序和每条规则的参数如下，命中哪一条会写在结论里：

| 顺序 | 规则 | 源码里怎么判 |
|---|---|---|
| 0 | 相同 | 候选和基线内容完全一样，直接不合入，不花钱去跑 |
| 1 | 回归 | 回归集里基线能稳定通过的任务，候选一条都不能退步 |
| 2 | 没涨 | 验收集通过率没有提高，不合入 |
| 3 | 噪声 | 涨幅不超过 `--min-gain`，不合入。填的是小数，0.1 表示 10 个百分点；默认是 0，等于没设 |
| 4 | 成本 | 平均用量超过基线的 1.5 倍，直接不合入（没有做「交给人判断」这一档） |

![配套源码里准入闸门的判定顺序：候选版本依次过回归、没涨、噪声、成本四条规则，回归集里基线稳定通过的任务一条都不能退步，验收集通过率要有提高，涨幅要超过设定的门槛，平均用量不能超过基线的 1.5 倍；命中任何一条就不合入，全部通过才合入](https://font-end-journey-resources.oss-cn-hangzhou.aliyuncs.com/images/project-ee-side-effects-admission-gate-v1.dark.png)

*图：表里第 1 到 4 条规则的判定顺序。第 0 条（候选和基线完全相同）在这之前就挡掉了，图里没有画。*

和上面的设计不一样的地方，动手时要知道：

- **波动门槛要你自己设。** 源码不会替你测波动。先把同一个版本完整跑两遍，两遍通过率之差就是波动，再用 `--min-gain` 把门槛设在它之上。自带的验收集只有 6 条，一条任务的变化就是 17 个百分点，这也是为什么任务集要自己补。
- **成本上限是 1.5 倍，超了直接不合入。** 上面的设计是 1.3 倍并且交给人判断，源码没有做「交给人」这一档。
- **回归没有退步预算。** 一条都不能退。
- **判定顺序不同。** 源码先跑回归集，因为它便宜而且一票否决，然后才跑验收集。
- **默认重复次数是 3。** 命令行的 `-n` 默认每条任务跑 3 次，不是 5 次。
- **没有人工复核队列这一步。** 上面说从失败变为通过的任务要送去人工复核，源码里只有评分器那边的抽检队列（每 10 次判定抽 1 次给人看），没有「失败变通过就送复核」的队列，准入流程也不接人工，留作练习。
- **成本只算 token。** 设计里说的是花费或耗时，源码只比 token 花费。
- **验收集没有做抽取和退役。** 每次准入用的是全部验收任务。使用次数的记录和轮换留作练习。

回归判定和设计一致，只看基线能稳定通过的任务。基线本来就不通过的不计入，合入时的结论里会写「另有几条基线本来就不通过，不计入」。它们不通过说明的是任务或基线有问题，不是候选退步了。

回归集里有两条「不该动手」的任务：一条是代码本来就对、只要求跑测试并报告结论，一条是只要求解释一段代码。它们对应任务集一章说的反向任务。改提示词很容易把 Agent 推向「见什么都改」，这两条任务就是用来在闸门上拦住这种退步的。

## 闸门挡不住的三件事

- **任务分布的漂移。** 三套任务集都是过去收集的。真实使用中出现了全新类型的任务，闸门不会知道。办法只有持续从真实使用里补充任务。
- **评分器的漏洞。** 闸门完全信任评分器。评分器有误放，闸门就会放行钻漏洞的版本。所以审计必须先于进化。
- **在线更新。** 经验手册的在线模式会在没有经过闸门的情况下改变 Agent 的行为。要用在线模式，至少做到条目可追溯、可按条回退，并且定期把当前手册作为候选过一次闸门。

第二篇论文摘要里强调持续验证和独立保障，说的也是这个意思：一道闸门不是一劳永逸的保证。

## 回退

每个版本都记录了父版本，回退就是把当前版本指回某个祖先。难的是决定退到哪里：

1. 用二分法在版本链上定位是哪一次合入引入了问题。
2. 把那次合入之后的修改逐个在它的父版本上重新过闸门，能过的保留。

所以每次合入的修改要小。一次合入包含十处改动，回退时就只能十处一起丢掉。

## 这个项目最终想让你讲出的故事

整个项目连起来是这样一条线：我为自己的 Agent 建了评测，审计后发现并修正了评分漏洞；在可信的评测上实践了四个级别的自进化；观察到进化会带来遗忘，并用独立的验收数据和回归检查来约束它；最后给出各级别在提升、遗忘和成本三个维度上的对比。

每一个数字都来自你自己的任务集。这个故事的说服力不在于提升了多少，而在于你清楚每一个结论能信到什么程度。

## 自己动手时的检查点

1. 把任务分成两到三类，做一次分阶段进化，填出完整的结果表。
2. 分别在关闭和打开回归检查的情况下做一遍，对比遗忘量。
3. 实现完整的准入闸门，统计一段进化过程中被每条规则拒绝的候选各有多少。
4. 人为制造一个引入退步的合入，练习用二分法定位并回退。

## 面试常见追问

- **自进化有什么风险？** 遗忘旧能力、过拟合验收集、钻评分漏洞、成本失控。
- **怎么防止改好一个改坏另一个？** 回归集、最小化修改、合入前的独立验收、可回退的版本链。
- **验收集会不会也被过拟合？** 会，讲使用次数、轮换和补充，以及最终只用一次的留出任务。
- **上线后还能继续进化吗？** 讲在线更新的风险和约束：可追溯、可回退、定期过闸门、不自动放宽权限。
