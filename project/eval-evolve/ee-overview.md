第一个项目造出了一个 Agent。这个项目回答接下来的两个问题：它到底好不好，以及能不能让它自己变好。做完之后你手里有一个平台：一头接上任何一个 Agent 就能给出可信的评测结论，另一头能自动提出改进并且只放行真正变好的版本。

这个项目的每一章都对应一篇近两年的论文或一线团队的工程文章。你做的是把论文里的方法缩小规模，在自己的 Agent 和自己的任务集上跑一遍。

## 做出来是什么样

```text
$ evo eval --agent ./my-agent --suite coding-v3 --repeat 5

版本 v12   任务 40 条 × 5 次
  至少成功一次      85.0%
  每次都成功        50.0%
  平均每条花费      ¥0.19    平均耗时 71 秒
  不稳定的任务      14 条（见 report/flaky.md）

$ evo evolve --level prompt --rounds 6

第 1 轮  读取 14 条失败轨迹，归因：9 条没有运行测试就结束
        提出 3 个候选提示词
        验收集：v12 62% → 候选 B 71%   回归集：无退步   合入为 v13
第 2 轮  ……
第 4 轮  候选 A 验收集 +4%，回归集 2 条任务退步   拒绝合入
```

上面是目标形态的示意，数字是占位，你的结果取决于任务集和模型。

## 为什么评测和进化放在一个项目里

自进化的每一步都在问同一个问题：新版本比旧版本好吗。回答不了这个问题，进化就是随机改动。所以顺序是固定的：先把尺子造准，再谈用尺子指导修改。

| 部分 | 回答的问题 | 章节 |
|---|---|---|
| 评测 | 这一版 Agent 怎么样，结论有多可信 | 任务集、评分器、可靠性报告、审计评分器 |
| 自进化 | 怎样自动提出修改，怎样判断该不该合入 | 四个级别的进化、副作用与准入 |

这也是面试官追问最多的一条线。牛客上大厂 Agent 岗的面经里，对项目追问最集中的不是用了什么技术，而是效果怎么量化、评测集怎么建、怎么做回归、出了错怎么发现。

## 每一章依据什么

| 章 | 做什么 | 依据 |
|---|---|---|
| 任务集与数据划分 | 从真实失败里建任务，划分进化集、验收集、回归集 | Anthropic《Demystifying evals for AI agents》 |
| 评分器 | 代码判定、模型裁判、人工抽检，裁判要校准 | 同上 |
| 可靠性与成本报告 | 同一任务跑多次，报告稳定性和成本 | Princeton 等《Emerging Trends in AI Agent Evaluation》 |
| 审计评分器 | 注入已知错误，检查评分器能否查出 | 《When Agent Evaluation Becomes Unreliable》 |
| 第一级：进化提示词 | 读失败轨迹反思并改写提示词 | GEPA |
| 第二级：进化经验手册 | 增量维护一本经验手册 | ACE |
| 第三级：进化配置与工具 | 挖掘弱点、提出最小修改、回归验证 | Self-Harness |
| 第四级：进化外壳代码 | 让编程 Agent 读历史版本并写出新版 | Meta-Harness |
| 进化的副作用 | 改好新任务时改坏旧任务，以及怎样把关 | 《Are Self-Evolving Agents Continual Learners?》《Self-Evolving Agent Harness》 |

论文链接放在各章末尾。

## 需要先说清楚的三件事

**规模是缩小的。** 论文的实验在 SWE-bench、Terminal-Bench 这类大型基准上进行，一轮的花费很高。本项目在你自己的几十条任务上、用便宜的模型来跑。你得到的是“这个方法在我的任务集上的表现”，不能写成复现了论文的数字。

**四级都是按论文思路自己实现的简化版。** 四篇论文都公开了官方代码，可以拿来对照。本项目不直接调用它们，而是让你在自己的 Agent 上把每一步亲手写一遍，规模也小得多。章节里会标明哪些是论文的做法、哪些是本项目的设计。

**效果可能不明显。** 在几十条任务上，进化带来的提升有可能淹没在随机波动里。这种情况下如实分析“为什么没有提升”同样是一份合格的结果，可靠性一章会教你怎样判断一个提升是不是真的。

## 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 被测对象 | 第一个项目的通用 Agent | 你完全了解它，改得动它的每一层 |
| 语言 | Python 3.11 及以上 | 与被测对象一致 |
| 存储 | SQLite + 文件 | 结果入库，轨迹和版本以文件保存，便于比对 |
| 隔离 | 每条任务一个临时目录，可选容器 | 评测结果可复现的前提 |
| 报告 | 命令行表格 + 静态网页 | 不需要单独的前端工程 |

没有做第一个项目也可以开始：平台对被测对象只有一个要求，即能在无界面模式下接收任务、输出结果和轨迹。

## 四段路线

| 阶段 | 章节 | 做完能讲什么 |
|---|---|---|
| 第一段：造尺子 | 架构、任务集、评分器 | 我为自己的 Agent 建了一套评测，知道它在哪些任务上失败 |
| 第二段：校尺子 | 可靠性报告、审计评分器 | 我发现并修正了自己评测里的假阳性 |
| 第三段：浅层进化 | 提示词、经验手册 | 我在自己的任务集上实践了 GEPA 和 ACE |
| 第四段：深层进化与把关 | 配置与工具、外壳代码、副作用 | 我的 Agent 能提出对自身的修改，并且有一道闸门防止它改坏自己 |

第二段结束就已经是一个完整的评测项目。后两段是在同一个平台上继续加东西。

## 开始之前需要会什么

- 读过第一个项目的评测一章，知道任务集、评分器、多次运行这几个概念。
- 能读英文论文的摘要和方法部分。每章会讲清楚要点，但面试时被问到细节，读过原文和没读过差别很大。
