Agent 上线之后总有任务做不好。这个项目给它配一个“夜班教练”：让它每晚自己复盘白天的失败、自己动手改自己，改完去考试，考过了新版本才上线，没考过就原样退回。这件事有个正式的名字，叫 RSI（递归自我改进）。

## 背景：为什么做这个项目

接着项目一说。那个会修 bug 的编程 Agent 做出来、上线了，然后你会遇到一件每个做 Agent 的人都遇到过的事：

- 用户反馈它有一类任务总做不好。你看了几条失败记录，往提示词里加了一句话。
- 这类任务好了。过两天发现，另一类原来没问题的任务开始出错。
- 你再加一句话补救。提示词越来越长，没人说得清哪一句还在起作用。

手动调 Agent 就是这样，改好一个、坏掉两个，而且全凭感觉。问题不在于你不够细心，而在于这个流程里少了两样东西：一把能回答“新版本到底比旧版本好没好”的尺子，和一道“没变好就不许上线”的闸门。

有了这两样东西，改的那一步就可以交给 Agent 自己做。它读失败记录比人快，一晚上能试的修改比人多；尺子和闸门保证它试出来的东西只有真的变好才留下。牛客上大厂 Agent 岗的面经里，对项目追问最集中的也正是这一块：效果怎么量化、评测集怎么建、怎么做回归、怎么保证改了不出事。

所以这个项目分两部分，顺序是固定的：先把尺子造准，再让 Agent 在尺子的把关下自己改自己。

| 部分 | 回答的问题 | 章节 |
|---|---|---|
| 评测 | 这一版 Agent 怎么样，结论有多可信 | 任务集、评分器、可靠性报告、审计评分器 |
| 自进化 | 怎样让它自己提出修改，怎样判断该不该上线 | 四个级别的进化、副作用与准入 |

RSI 这个概念的来历、现在工程上改的到底是什么、它做不到什么，下一章单独讲。

## 目标：做成什么

一句话的目标：**先造一把量得准的尺子，再让 Agent 在这把尺子的把关下一代一代地自己变好。**

![一轮自我改进的四步：先在练习题上摸底留下失败记录，Agent 自己复盘找共同原因，再动手改自己的提示词、手册、配置或代码，最后参加考试；考过了新版本上线并成为下一轮的起点，没过就原样退回](https://font-end-journey-resources.oss-cn-hangzhou.aliyuncs.com/images/project-ee-overview-improve-loop-v1.dark.png)

*图：一轮改进的四步。图里的练习题、新题、老题，对应后面各章说的进化集、验收集、回归集。*

拆开来是两条要求：

1. **评测结论可信。** 同一条任务跑多次，稳定性和成本一起报；评分器本身要经过审计，不能放过作弊。
2. **进化有闸门。** 自动提出的修改，只有在验收集上的提升超过波动范围、回归集上不退步、花费没有超出上限时才合入。

跑起来大致是这样：

```text
$ evo eval --agent ./my-agent --suite coding-v3 --repeat 5

版本 v12   任务 40 条 × 5 次
  至少成功一次      85.0%
  每次都成功        50.0%
  平均每条花费      ¥0.19    平均耗时 71 秒
  不稳定的任务      14 条（见 report/flaky.md）

$ evo evolve --level prompt --rounds 6

第 1 轮  读取 14 条失败轨迹，归因：9 条没有运行测试就结束
        提出 3 个候选提示词
        验收集：v12 62% → 候选 B 71%   回归集：无退步   合入为 v13
第 2 轮  ……
第 4 轮  候选 A 验收集 +4%，回归集 2 条任务退步   拒绝合入
```

上面是目标形态的示意，数字是占位，你的结果取决于任务集和模型。

## 要做哪些事

目标拆成六件事，对应后面的章节。

| 要做的事 | 章节 | 做完能讲什么 |
|---|---|---|
| 弄清概念 | RSI 是什么 | RSI 从哪来、现在改的是什么、边界在哪 |
| 定方案 | 系统架构 | 评测和自进化两条链路怎么衔接，版本和运行记录怎么存 |
| 造尺子 | 任务集、评分器 | 我为自己的 Agent 建了一套评测，知道它在哪些任务上失败 |
| 校尺子 | 可靠性与成本、审计评分器 | 我发现并修正了自己评测里的假阳性 |
| 四级进化 | 提示词、经验手册、配置与工具、外壳代码 | 我的 Agent 能提出对自身的修改，其中前两级实践的是 GEPA 和 ACE 的思路 |
| 上线把关 | 进化的副作用与准入闸门 | 有一道闸门防止它改好新任务时改坏旧任务，连续多代时有编辑预算防止它越改越贴着练习题 |

做到“校尺子”就已经是一个完整的评测项目。后面的进化和把关是在同一个平台上继续加东西。

### 每一章依据什么

这个项目的每一章都对应一篇近两年的论文或一线团队的工程文章。你做的是把论文里的方法缩小规模，在自己的 Agent 和自己的任务集上跑一遍。

| 章 | 做什么 | 依据 |
|---|---|---|
| 任务集与数据划分 | 从真实失败里建任务，划分进化集、验收集、回归集 | Anthropic《Demystifying evals for AI agents》 |
| 评分器 | 代码判定、模型裁判、人工抽检，裁判要校准 | 同上 |
| 可靠性与成本报告 | 同一任务跑多次，报告稳定性和成本 | Princeton 等《Emerging Trends in AI Agent Evaluation》 |
| 审计评分器 | 注入已知错误，检查评分器能否查出 | 《When Agent Evaluation Becomes Unreliable》 |
| 第一级：进化提示词 | 读失败轨迹反思并改写提示词 | GEPA |
| 第二级：进化经验手册 | 增量维护一本经验手册 | ACE |
| 第三级：进化配置与工具 | 挖掘弱点、提出最小修改、回归验证 | Self-Harness |
| 第四级：进化外壳代码 | 让编程 Agent 读历史版本并写出新版 | Meta-Harness |
| RSI 是什么 | 概念的来历、四步循环、连续多代 | Gödel Machine、STOP、Darwin Gödel Machine、Lilian Weng 的 Harness 一文 |
| 进化的副作用 | 改好新任务时改坏旧任务，以及怎样把关 | 《Are Self-Evolving Agents Continual Learners?》《Self-Evolving Agent Harness》 |
| 编辑预算 | 一代最多改多少，不许把题目写进规则 | RRSI |

论文链接放在各章末尾。

## 预期结果：做完手里有什么

- **一份可靠性报告。** “至少成功一次”和“每次都成功”分开报，带平均用量、耗时和不稳定任务的清单。
- **一次评分器审计。** 对每条任务构造几种已知结果的运行，比如什么都不做、只声称修好、删掉测试，看评分器的判定和预期是否一致。
- **一份版本历史。** 每个候选修改是合入了还是被拒绝了，依据是哪一组对比数字。
- **四个级别的进化各跑通一轮。** 从改提示词到改外壳代码，过的是同一道准入闸门。
- **一份连续多代的升级记录。** 从一个只能做对一半的起点出发连跑几代，每一代发现了什么、改了什么、考了几分、上线还是被拦下，连同一棵版本树。在线试用里放了一次真实的五代运行。

源码是用来对照和兜底的。写进简历的那一版要你自己实现一遍，数字也要用自己跑出来的。

## 边界：需要先说清楚的四件事

**规模是缩小的。** 论文的实验在 SWE-bench、Terminal-Bench 这类大型基准上进行，一轮的花费很高。本项目在你自己的几十条任务上、用便宜的模型来跑。你得到的是“这个方法在我的任务集上的表现”，不能写成复现了论文的数字。

**四级和编辑预算都是按论文思路自己实现的简化版。** 这几篇论文大多公开了官方代码，可以拿来对照。本项目不直接调用它们，而是让你在自己的 Agent 上把每一步亲手写一遍，规模也小得多。章节里会标明哪些是论文的做法、哪些是本项目的设计。

**它不会无限变强。** 模型是冻结的，被改的只是包在模型外面的那层外壳，上限由模型的能力和任务集决定。连跑几代之后没有东西可改，是正常的收敛。

**效果可能不明显。** 在几十条任务上，进化带来的提升有可能淹没在随机波动里。这种情况下如实分析“为什么没有提升”同样是一份合格的结果，可靠性一章会教你怎样判断一个提升是不是真的。

## 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 被测对象 | 「从零手写通用 Agent」项目的 Agent | 你完全了解它，改得动它的每一层 |
| 语言 | Python 3.11 及以上 | 与被测对象一致 |
| 存储 | SQLite + 文件 | 结果入库，轨迹和版本以文件保存，便于比对 |
| 隔离 | 每条任务一个临时目录，可选容器 | 评测结果可复现的前提 |
| 报告 | 命令行表格 + 静态网页 | 不需要单独的前端工程 |

没有做过那个项目也可以开始：平台对被测对象只有一个要求，即能在无界面模式下接收任务、输出结果和轨迹。

配套源码为了拿到手就能跑，做了几处简化：命令是 `python -m evo.cli eval` 这样的形式，参数和上面的示意不完全一样，以源码的说明文件为准；报告只有命令行表格，成本按模型用量（输入和输出的 token 数）统计，没有换算成金额；隔离只做了临时目录，没有做容器。闸门里的波动门槛不会自动测，要自己用 `--min-gain` 设，默认是 0，也就是只要求验收集上有提升。源码自带 20 条任务，其中进化集 7 条、验收集 9 条、回归集 4 条，够把流程跑通，要得到可信的结论得自己把任务集扩充到几十条。

## 开始之前需要会什么

- 建议先读「从零手写通用 Agent」项目的评测一章，知道任务集、评分器、多次运行这几个概念。
- 能读英文论文的摘要和方法部分。每章会讲清楚要点，但面试时被问到细节，读过原文和没读过差别很大。
