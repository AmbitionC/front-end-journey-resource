素材写得好不好，首先取决于对商品的理解。这一环节把一堆商品详情和用户评价变成一份结构化的卖点清单，并且给每个卖点标上“能不能说、凭什么说”。

## 为什么不直接让模型写文案

把商品详情丢给模型让它直接写广告，会得到流畅但有问题的文案：

- 写出详情里没有的功效，例如把“清爽”发挥成“控油祛痘”。
- 把商家的宣传语当成事实，例如“销量第一”。
- 每次抓的重点不一样，后面没法做归因。

先提取卖点再写文案，等于在商品和素材之间加了一层可以检查、可以引用的中间表示。素材生成时只能使用清单里的卖点，归因时能把效果追溯到具体的卖点。

## 卖点的结构

```python
@dataclass
class SellingPoint:
    id: int
    text: str              # 卖点本身，如“不含酒精”
    category: str          # 功效 / 成分 / 使用感 / 规格 / 价格 / 服务
    evidence: str          # 原文依据，逐字摘自详情或评价
    source: str            # detail | review | spec
    claim_level: str       # verified | needs_proof | forbidden
    review_support: int    # 有多少条评价提到了它
```

`evidence` 必须是逐字摘录。这和第一个项目研究模式里“摘录必须保留原文”是同一条规则：改写过的依据无法核对。

*依据必须能在原文里逐字找到，这一步由程序校验，不交给模型判断。*

### 从评价里提取

评价是比详情更有价值的来源。它告诉你真实用户在意什么，以及他们用什么词来说。

评价数量多时不要整批塞进上下文。按主题分批处理，每批提取出“提到的优点、提到的缺点、原话”，再合并计数：

```python
async def mine_reviews(reviews: list[str], batch: int = 50) -> list[ReviewTheme]:
    partials = await asyncio.gather(*(extract_themes(reviews[i:i + batch])
                                      for i in range(0, len(reviews), batch)))
    return merge_and_count(partials)     # 相同主题合并，累加提及次数，保留代表性原话
```

缺点同样要保留。评价里集中出现的缺点，例如“搓泥”，决定了哪些话不能说，也常常提示了应该避开哪类人群。

### 校验依据

模型给出的依据可能是它自己编的。提取之后做一次程序检查：

```python
def evidence_ok(sp: SellingPoint, corpus: str) -> bool:
    return normalize(sp.evidence) in normalize(corpus)
```

`normalize` 只去掉空白和标点差异。找不到依据的卖点直接丢弃，不进入后续环节。

## 声明等级

这是本环节最重要的输出。每个卖点分到三个等级之一：

| 等级 | 含义 | 例子 | 素材里能否使用 |
|---|---|---|---|
| verified | 规格参数或可直接核实的事实 | 容量 50ml、不含酒精（成分表可查） | 可以 |
| needs_proof | 功效或对比类的声明，需要资质或检测报告支持 | SPF50+、防水、敏感肌适用 | 人工确认有依据后才可以 |
| forbidden | 法规或平台规则明确不允许的说法 | 医疗功效、绝对化用语 | 不可以 |

模型负责初判，判断依据写在提示词里：

```text
对每个卖点判断声明等级：
- 可以由规格表或成分表直接核实的客观事实，标 verified。
- 涉及功效、效果程度、适用人群、与其他产品比较的，标 needs_proof。
- 涉及疾病治疗或预防、使用“最”“第一”“唯一”等绝对化表述的，标 forbidden。
拿不准时标 needs_proof。
```

“拿不准时往严的方向标”是整个项目处理合规问题的统一原则。

`needs_proof` 的卖点全部进入人工确认。模型无法知道这款防晒有没有对应的检测报告，这件事只有人能回答。看板上列出每个待确认的卖点和它的原文依据，人点一下确认或删除。

防晒这个例子有它的特殊性：防晒类产品在我国按特殊化妆品管理，防晒指数这类功效宣称需要有相应依据。教程用它做例子，正是因为它能把“哪些话需要证据”这个问题暴露得很充分。具体到你选的品类，适用哪些规定需要你自己查证，本教程的示例不构成法律意见。

## 输出给下游的是什么

下游环节拿到的不是全文，而是一份紧凑的清单：

```text
卖点清单（商品 1024，共 6 条可用）
#3  成分  不含酒精            verified   评价提及 41 次
#5  使用感 成膜快、不黏腻       verified   评价提及 87 次
#7  功效  SPF50+ PA++++      已确认     评价提及 23 次
#8  规格  50ml 便携装         verified   评价提及 12 次
……
不可使用：#2（“防晒效果第一”，绝对化用语）
需避开：评价中 19 次提到“叠加粉底会搓泥”
```

“需避开”一栏会被素材生成和人群分层用到。

## 这个环节怎么评测

准备十来个商品，每个商品人工标注一份卖点清单作为参照，评三件事：

| 指标 | 怎么算 | 用什么判 |
|---|---|---|
| 依据有效 | 卖点的依据能在原文中逐字找到的比例 | 程序 |
| 覆盖 | 人工清单里的卖点被提取出来的比例 | 模型裁判判断两条卖点是否同义 |
| 等级准确 | 声明等级和人工标注一致的比例，重点看有没有把该拦的标成可用 | 程序 |

第三项里，把 `forbidden` 或 `needs_proof` 错标成 `verified` 是最严重的错误，要单独统计。

## 自己动手时的检查点

1. 选一个你熟悉的品类，准备 10 个商品的详情和评价。可以用公开的商品评论数据集，也可以手工整理。
2. 实现提取和依据校验，统计有多少条卖点因为依据找不到被丢弃。
3. 人工标注声明等级，和模型初判对比，记下错标成可用的条数。
4. 把提及次数最多的缺点找出来，想想它应该怎样影响后面的素材。

## 面试常见追问

- **怎么防止生成的文案夸大或失实？** 卖点清单作为唯一素材来源、依据逐字校验、声明等级、人工确认。
- **为什么要加一层卖点而不是直接生成？** 可检查、可引用、可归因。
- **评价很多怎么处理？** 分批提取、合并计数，不把全量评价放进上下文。
- **模型判断不了的合规问题怎么办？** 往严的方向标，交给人确认，并说明哪些事只有人能回答。
