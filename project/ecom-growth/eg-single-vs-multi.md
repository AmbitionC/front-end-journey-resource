这个项目把一次活动拆成了一个主管和多个环节，其中要调模型的环节各有自己的上下文。面试官很可能直接问：为什么不用一个 Agent 加几个 Skill 做完？多 Agent 是不是为了显得复杂？

这个问题不能靠讲道理回答。这一章在源码里把另一种做法也实现出来，让两种做法跑同一次活动，用数字回答。

## 两种做法各是什么

**多环节，各有上下文。** 也就是前面各章的做法。写素材的环节拿到的是人群描述和卖点清单，审核的环节拿到的是待审文案和规则，归因的环节拿到的是投放数据。每次调用都是一段新的、只装着这一步所需信息的上下文。环节之间只通过数据层交接编号。

**一个上下文加 Skill。** 只有一条对话。各环节的提示词不再是独立的系统提示词，而是写成 Skill：平时只有一行简介，用到时才把全文加载进对话，之后一直留在里面。每一步的任务和模型的回复都接在同一条对话后面。对话超过长度上限时，把最早的步骤折叠掉。

第二种做法这两年很流行，原因是它简单：不用设计环节之间传什么，模型自己看得到前面发生的一切。Anthropic 在《Building effective agents》里的建议是先找最简单的方案，只有在更简单的方案确实不够用时才增加复杂度。所以默认的立场应该是：先假设单上下文够用，拆分需要理由。

## 实验怎么设计才公平

对照实验最容易犯的错是两边差了不止一个变量。如果另一种做法顺手换了提示词、少了几道检查，跑出来的差距就说不清是谁造成的。

源码里的做法是只换一个东西（下面的代码有删节，完整的在 `growth/single.py`）：

```python
class ThreadStage:
    """把一个环节的调用接到那条对话上。环节代码不用改：它以为自己还在调自己的模型。"""

    async def ask(self, system: str, user: str, *, data=None) -> str:
        async with self.thread.lock:        # 一条对话一次只能做一件事
            prompt = self.thread.render(self.stage, system, user)
            reply = await self.base.ask(SINGLE_SYSTEM + skill_catalog, prompt, data=data)   # 系统提示词后面跟着各 Skill 的一行简介
            self.thread.steps.append((self.stage, user, reply))
            return reply
```

环节原来传进来的系统提示词被当成 Skill 的正文，第一次用到时加载；任务说明接在对话末尾。除此之外全部相同：

| 保持一致 | 说明 |
|---|---|
| 环节的代码和提示词 | 同一套 `growth/stages/` |
| 主管的决策规则和代码闸口 | 没过审核的素材照样进不了试投 |
| 规则层审核 | 规则是代码，不受上下文影响 |
| 试投环境和归因的统计 | 扮演用户的模型不属于被比较的对象，两边都走独立调用 |

这样两边的差距只能归到「上下文怎么组织」这一个变量上。

## 量三件事

**花费。** 一条对话越写越长，每次调用都要把前面的内容重新读一遍。多环节的做法里，每次调用只读这一步需要的那一小段。

**并行。** 一条对话一次只能做一件事。原来十几版素材可以同时写、同时审，现在只能排队。

**审核独立性。** 这是最容易被忽略的一项。单上下文里，审核的人就是写文案的人，而且它看得到自己刚才的写作思路。人审自己的稿子容易放水，模型也一样。怎么量：把这次活动里通过审核的素材，交给一个没有任何上下文的审核员再审一遍，数它拦下几版。多环节那一边也做同样的复查，得到的是审核员自己前后不一致的底数，两个数相减才是「自己审自己」多放过去的。

```bash
python -m growth.cli compare --offline            # 不接模型，几秒钟
python -m growth.cli compare --max-calls 1500     # 接真模型，两边各跑一次
```

## 离线能看出什么

不接模型时，源码用一个离线替身代替模型。它按规则生成内容，不看上下文，所以两边写出来的东西一模一样，能看出来的只有花费的量级。默认规模（2 轮、每类人群 3 版）下的结果：

| 指标 | 多环节，各有上下文 | 一个上下文加 Skill |
|---|---|---|
| 模型调用次数 | 159 | 159 |
| 输入字符数 | 约 6.4 万 | 约 550 万 |
| 单次调用最长的输入 | 约 1400 字符 | 约 6 万字符（到了上限） |
| 折叠掉的早期步骤 | 0 | 5 |

调用次数相同，输入量差了八十多倍。原因很直接：159 次调用，每次都带着前面的步骤，超出上限的部分才被折叠。

这个数字要打两个折扣再讲。第一，接口支持前缀缓存时，重读的部分会便宜很多，实际的费用差距远小于字符数的差距，但不会变成零；缓存也解决不了一条对话只能排队执行的问题。第二，这里的每一步都很短；真实任务里单步的输出更长，对话会更早撞到上限，折叠会更频繁，被折叠掉的信息对后面步骤的影响也要算进去。

## 接上真模型要看什么

离线替身看不出质量上的差别。接上真模型后，重点看三行：

| 指标 | 你的结果 | 怎么读 |
|---|---|---|
| 用时 | 【多环节】秒 对【单上下文】秒 | 排队带来的差距 |
| 首次送审被拦的比例（只算第 1 轮） | 【】对【】 | 第 1 轮写稿时审核的 Skill 还没加载，两边条件基本相同。想看「写的时候看得到审核细则」有没有帮助，要比后面几轮的拦截情况 |
| 独立复查拦下的版数 | 【】对【】 | 两边之差是「自己审自己」多放过去的 |

这张表请用你自己的运行记录填。同一种做法跑两遍，结果也会不一样，所以每边至少跑三次再下结论，只差一两版的不要当成结论。

不要预设答案。如果你的结果是单上下文在审核独立性上没有变差、花费在缓存之后也能接受，那么如实写「在这个规模上拆分的理由不充分」，这同样是一个合格的结论，而且比背一段多 Agent 的好处更能说明你做过。

## 什么时候该拆

把这个项目的经验推广一点，拆成独立上下文的理由只有这几类：

- **需要独立的判断。** 审核、评分、验收这类环节，判断者不应该看到被判断内容的创作过程。
- **可以并行。** 互不依赖的一批工作，拆开才能同时做。
- **单步的输入很大。** 一步要读几万字的材料，读完只需要留下几行结论。放在主对话里，这几万字会一直占着位置。
- **不同环节适合不同的模型。** 推理强的做归因，便宜的做量大的简单判断。单上下文里换模型，缓存会失效。

反过来，这些情况不该拆：步骤之间强依赖、后一步需要前一步的细节而不只是结论；任务本身很短；或者拆开之后大部分精力花在设计环节之间传什么上。

这个项目里，试投和归因之间传的是数据而不是文字，审核需要独立性，写稿和模拟打分可以大量并行，所以拆是有理由的。主管的决策就不一样：它只是几次很短的调用，放在哪里都行。

## 自己动手时的检查点

1. 离线跑一遍 `compare`，确认两边调用次数相同、输入量差距在一个量级以上。
2. 把 `growth/single.py` 里 `max_chars` 的默认值从 60_000 改成 20_000 再跑一遍，看折叠次数怎么变；想一想被折叠掉的步骤里有哪些是后面还会用到的。
3. 接上真模型，每边跑三次，填出上面那张表，写一段不超过五句话的结论。
4. 只把审核一个环节放回独立上下文（在 `growth/single.py` 的 `OUTSIDE` 里加上 `"review"`），其余留在单上下文里，再量一次。这种混合做法常常是实际项目的答案。

## 面试常见追问

- **为什么用多 Agent，不用一个 Agent 加 Skill？** 先承认默认应该用单个，再讲这个项目里拆分的三个理由，最后给出你自己的对照数字。
- **多 Agent 的代价是什么？** 环节之间传什么要设计，信息在交接中会丢，出了问题要跨环节追。
- **单上下文的成本问题，缓存不是能解决吗？** 能缓解费用，解决不了排队，也解决不了审核者看得到创作过程。
- **你的对照实验公平吗？** 讲只换了一个变量，哪些保持一致；也讲局限：试投环境是模拟的，规模小，重复次数有限。
