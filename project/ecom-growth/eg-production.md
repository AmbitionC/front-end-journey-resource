闭环跑通之后，最后一章处理让它像一个真实系统的几件事：一次活动要调多少次模型、怎样又快又省、中途断了怎么办、多个活动同时跑怎么办。字节的一道面试设计题问的正是这些：一个文案生成 Agent，要求高并发下低延迟、成本可控、文案合规。

## 先算账

以一次典型的活动为例，数一数模型调用的次数（按 4 类人群、每类 4 版、4 轮、每轮 2000 次曝光估算）：

| 环节 | 调用次数的量级 | 说明 |
|---|---|---|
| 商品理解 | 十几次 | 评价分批提取 |
| 人群分层 | 几次 | |
| 素材生成与自检 | 每轮 30 到 40 次 | 首轮最多，后面只生成改写的 |
| 审核的模型裁判 | 每版素材 6 次 | 每个检查项一次 |
| 模拟用户打分 | 每轮上千次 | **最大头** |
| 归因的反馈归纳 | 每轮十几次 | |
| 进化改写 | 每轮十来次 | |

这是估算的方法，具体数字请用你自己的运行记录替换。

结论很清楚：成本和耗时的大头在模拟用户打分。优化要从这里下手，而不是去省主管那几次调用。真实系统里没有这一项，取而代之的大头通常是素材生成和审核。

每次调用都记录环节、模型、输入输出用量和耗时，汇总成一张按环节分的成本表。没有这张表，所有的优化都是在猜。

## 降成本的四个办法

**缓存。** 模拟环境一章已经定了规则：同一对“素材内容和用户”只打一次分。一版素材活过四轮，它和同一批用户的相关程度不需要重算。键用内容的哈希值而不是素材编号，内容相同的改写版本也能命中。

**分级用模型。** 不同环节对模型能力的要求差别很大：

| 环节 | 需要什么 | 用什么 |
|---|---|---|
| 主管决策、归因、改写时的诊断 | 推理能力 | 能力强的模型 |
| 写文案正文 | 表达能力 | 中等模型通常足够 |
| 自检、审核的单项判断、模拟用户打分 | 简单的阅读理解，量大 | 便宜的模型 |

每个环节换成便宜模型之前，先在该环节的评测集上确认质量没有明显下降。审核环节尤其要看漏放率。

**利用前缀缓存。** 模拟用户打分时，同一版素材要配上千个不同的用户。把素材和打分说明放在提示词前面，用户设定放在最后，前面的部分就能重复命中缓存。素材生成时同理，商品卖点和人群描述放前面，方案放后面。

**先抽样再放量。** 一轮 2000 次曝光不必一次打完。先打 400 次，那些已经明显落后的素材不再继续分配曝光，剩下的预算集中在还分不出高下的素材上。这和汤普森采样的思路一致，只是用在了节省模拟成本上。

## 并发与限流

上千次打分调用必须并行，而模型接口有每分钟的请求数和用量限制。

```python
class RateLimitedPool:
    def __init__(self, max_concurrency: int, rpm: int):
        self.sem = asyncio.Semaphore(max_concurrency)
        self.bucket = TokenBucket(rate=rpm / 60, capacity=rpm // 6)

    async def call(self, fn, *args, retries: int = 4):
        for attempt in range(retries):
            await self.bucket.acquire()
            async with self.sem:
                try:
                    return await fn(*args)
                except RateLimitError as e:
                    await asyncio.sleep(e.retry_after or 2 ** attempt + random.random())
                except TransientError:
                    await asyncio.sleep(2 ** attempt + random.random())
        raise GiveUp
```

三个要点：

- **并发数和速率是两个限制。** 信号量管同时在途的请求数，令牌桶管单位时间的请求数，两者都要有。
- **退避要带随机量。** 一批请求同时被限流，又同时在两秒后重试，会再次同时被限流。
- **按环节分池。** 模拟打分和素材审核各用各的池。否则上千次打分把配额占满，审核只能排队，整个流程卡在闸口上。

## 延迟

区分两类延迟：

| | 交互延迟 | 批处理耗时 |
|---|---|---|
| 是什么 | 用户在看板上点了确认之后多久看到反馈 | 一轮试投跑完要多久 |
| 目标 | 几秒内有响应 | 可以是几分钟，但要有进度 |
| 办法 | 立即返回任务编号，进度通过事件流推送 | 并行、缓存、分级模型 |

一轮试投不应该是一个要等几分钟才返回的请求。接口立刻返回，后台执行，看板订阅进度：

```text
第 2 轮试投　　　　已完成 1240 / 2000 次曝光
  敏感肌 × #152    点击 31 / 310
  ……
```

## 断点续跑

一次活动要跑十几分钟到几十分钟，中间可能因为接口故障或进程重启而中断。

状态的落点已经在架构一章定下了：所有环节通过数据库交接。所以续跑只需要让每个环节都是可重入的：

- 每个环节开始时先查数据库，已经完成的部分跳过。素材已经生成的不再生成，已经审过的不再审，已经记录的曝光不再重打。
- 写入时用确定性的键。一次曝光的键是“轮次、素材、用户”，重复写入不会产生第二条记录。
- 主管的会话记录照常落盘，恢复时读回。恢复后的第一件事是让它查询当前活动的状态，而不是依赖对话历史里的记忆。

试投是花钱的动作，要特别防止重复执行。给每一轮试投一个唯一的编号，执行前检查这个编号是否已经执行过。

## 多个活动同时跑

把活动当作一等对象。每张表都带 `campaign_id`，每个活动有独立的预算、独立的模拟用户池配置、独立的进度。

共享的只有模型接口的配额。多个活动同时跑时，各环节的调用池在活动之间按公平的方式分配，避免一个大活动把所有配额占掉。最简单的做法是给每个活动一个并发上限。

## 预算的硬闸

系统里有两种预算，都由代码强制，模型无法越过：

| 预算 | 含义 | 强制方式 |
|---|---|---|
| 投放预算 | 活动的曝光总量 | 分配器在分配前检查剩余量 |
| 运行预算 | 这次活动最多花多少模型调用费 | 每次调用前检查累计花费，超出则停止并保存状态 |

运行预算在模拟环境里尤其重要。一个配置错误（例如把每轮曝光多写了一个零）可以在几分钟里烧掉很多钱。

## 可观测

每次活动留下一条完整的链路：主管的每个决定、每个环节的输入输出编号、每次模型调用的用量和耗时。排查问题时按活动编号就能还原全过程。

看板上除了业务数据，再放四个运行指标：各环节的耗时、各环节的花费、审核拦截率的走势、失败和重试的次数。

## 回答那道设计题

把这一章的内容按面试题的三个要求组织起来：

| 要求 | 回答要点 |
|---|---|
| 高并发 | 无状态的生成服务横向扩展；信号量加令牌桶；按环节分池；活动之间公平分配 |
| 低延迟 | 交互请求立即返回、异步执行、推送进度；前缀缓存；分级用模型；能并行的并行 |
| 成本可控 | 按环节记账找到大头；结果缓存；便宜模型做量大的简单判断；运行预算硬闸 |
| 文案合规 | 规则、模型裁判、人工三层；审核是唯一通道；改写后重新送审；留痕 |

再补一句取舍：合规的检查不能为了延迟而跳过或并行到发布之后，它在关键路径上。能优化的是让规则层先行，挡掉大部分问题，减少进入模型裁判的量。

## 自己动手时的检查点

1. 产出一张按环节分的成本和耗时表，确认最大头是哪一项。
2. 打开缓存前后各跑一次相同的活动，对比调用次数。
3. 在试投进行到一半时强行结束进程，重启后确认没有重复的曝光记录。
4. 把运行预算设得很低，确认系统在超出时停下并保存了状态。

## 面试常见追问

- **成本怎么控制？** 先讲按环节记账，再讲四个办法，说出你自己测到的大头在哪。
- **高并发下怎么保证稳定？** 并发数和速率双重限制、带随机量的退避、分池、公平分配。
- **任务中断了怎么办？** 环节可重入、确定性的写入键、花钱的动作防重复。
- **哪些环节可以用便宜模型？** 按环节对能力的需求分级，并说明换模型前要在评测集上验证。
