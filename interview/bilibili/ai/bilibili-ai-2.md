### 哔哩哔哩 AI 应用岗一面：端到端 AI Coding 与生产治理（2026 年 8 月）

这轮面试要求从零说明端到端 AI Coding 的工程链路，覆盖 MCP 日志、DAG 状态、超时排查、灰度发布、Token 预算、模型路由与子 Agent。答案的重点是让每次自动化改动可验证、可观察、可回滚。

#### （1）端到端 AI Coding 的最小闭环是什么？

从需求开始，先把目标、影响范围、约束和验收标准结构化；再检索相关代码、文档与历史变更，形成计划。执行阶段让 Agent 在受限环境中修改小范围文件，运行格式化、类型检查、测试和安全扫描；最后由 diff、测试结果和人工/自动 Review 决定是否合入。每一步都应保存输入版本、工具调用、产物、验证证据和状态，失败时回到最近安全检查点而不是把长对话继续堆下去。

延伸阅读：[Coding Agent 的架构与执行循环](../../../knowledge/llm/agent/agent-coding.md)、[Agent 质量门禁](../../../knowledge/llm/production/agent-quality-gates.md)。

#### （2）已有日志 MCP 时，怎样把它接入问题定位而不污染上下文？

把日志能力包装为窄工具：明确服务、时间窗、环境、trace/request ID、字段白名单和最大返回量。Agent 应先根据告警或用户现象生成假设，再按 trace 关联请求、依赖和版本，并把大日志聚合为错误率、慢调用、关键样本和可追溯链接；原始敏感字段必须脱敏且按权限过滤。

日志是证据，不是指令。工具返回内容要被标记为不可信数据，不能因日志文本中的任意内容改变权限或执行命令；诊断结论也应附证据和置信边界。

延伸阅读：[MCP / A2A 智能体通信协议](../../../knowledge/llm/agent/mcp-protocol.md)、[Agent 可观测性与全链路 Tracing](../../../knowledge/llm/production/ai-observability.md)。

#### （3）AI Coding 的 DAG 任务状态应存在哪里？

它属于可恢复的工作流状态，而不是模型长期记忆。持久化层保存任务 ID、输入和代码版本、节点依赖、状态迁移、尝试次数、产物引用、权限/预算以及幂等键；大文件、日志和补丁只存对象引用。运行内存可缓存当前上下文，短期对话摘要可辅助推理，但都不能成为恢复任务的唯一事实来源。

状态迁移应由服务端校验，例如任务只能从已验证节点进入下一节点；并行分支通过明确的 reducer 或汇合节点合并。这样 worker 重启、模型切换或人工介入后仍能从检查点重放。

延伸阅读：[Agent 状态机](../../../knowledge/llm/agent/agent-state-machine.md)、[Agent 状态存储](../../../knowledge/backend/storage/agent-state-storage.md)。

#### （4）线上接口超时时，排查顺序是什么？

先确认超时发生在客户端、网关、应用、模型/工具还是数据库，并用 request ID/trace ID 划定受影响版本、区域与流量比例。查看 P50/P95/P99、连接池与队列等待、CPU/内存/GC、下游耗时和重试量；不要一开始就盯单条慢日志。随后区分偶发尖刺、容量饱和、依赖退化、死锁/阻塞和无限流式响应。

缓解措施包括合理的分层超时、取消传播、并发与队列背压、隔离慢依赖、熔断和有条件的重试。超时后的写操作需要幂等与结果查询，不能因为客户端没收到响应就断定服务器没有执行。

延伸阅读：[超时、重试、Fallback 与错误处理](../../../knowledge/llm/dev/llm-error-retry-fallback.md)。

#### （5）接口字段变更怎样灰度，才能让 Agent 和普通客户端都安全升级？

先采用向后兼容的演进：新增字段或新版本契约，旧字段在迁移期继续可用；消费者对未知字段忽略、对必填缺失 fail closed。对模型输出，使用版本化 Schema 与服务端校验，不能只依赖 Prompt 要求“按新格式返回”。

发布时以开关、租户或小流量分组逐步启用，监控 Schema 校验失败、空值率、业务成功率、延迟和回滚条件；在确认所有消费者迁移前不删除旧字段。契约测试与回放样本能提前发现模型/工具在字段变更后的兼容问题。

延伸阅读：[工具结果校验](../../../knowledge/llm/agent/agent-tool-result-validation.md)、[Agent 灰度、A/B 测试与实验隔离](../../../knowledge/llm/production/agent-ab-testing.md)。

#### （6）Token 有限时，如何进行大小模型协作和模型路由？

先根据任务风险、所需能力、上下文长度、结构化输出、数据合规、延迟和预算排除不合格模型，再在合格集合内选择质量/成本最合适的路线。小模型适合分类、抽取、格式检查和低风险草稿；大模型用于复杂规划、跨模块推理、疑难修复或小模型低置信升级。上下文先检索、摘要和裁剪，不能仅靠把任务“降给小模型”。

路由决定及其模型版本、Token、延迟、质量结果要写入 trace；有 fallback 时应重新评估约束，配合固定评测集和 Canary 验证，避免别名升级或降级悄悄改变产出。

延伸阅读：[模型路由与多供应商适配](../../../knowledge/llm/dev/llm-model-routing.md)、[Agent Prompt 回归与 Canary](../../../knowledge/llm/production/agent-prompt-regression.md)。

#### （7）为什么派生子 Agent？怎样避免派生后反而更差？

子 Agent 的价值是隔离上下文、权限和失败边界，并行处理相互独立的检索、测试或审查任务；它不是为了让更多模型同时“想一想”。父任务要给出明确目标、输入快照、可用工具、预算、截止时间和返回 Schema，子任务只回传必要结论与证据。

先用任务 DAG 识别真并行，限制总并发和扇出深度；共享写操作仍由单一 owner 串行提交。对子 Agent 设置取消、超时、预算和结果校验，并记录父子关联 trace，才能识别重复工作、上下文漂移和汇总阶段的幻觉。

延伸阅读：[Agent 子智能体](../../../knowledge/llm/agent/agent-subagents.md)、[Agent 并发控制](../../../knowledge/llm/production/agent-concurrency.md)。
