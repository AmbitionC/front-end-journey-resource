### 字节豆包 Seed Agent 开发一面：状态、容错与效果评测（2026 年 8 月）

这是一场约 70 分钟的 Agent 开发一面，问题沿着真实项目链路展开：会话状态、ReAct、工具容错、多 Agent、记忆、成本与评测。

#### （1）介绍 Agent 项目时，怎样讲清核心模块和端到端链路？

先说明用户目标和成功标准，再按“入口与鉴权 → 上下文构建 → 模型规划 → 工具执行 → 状态持久化 → 结果校验 → 观测评测”讲一条真实请求。每个模块都补充输入输出、失败处理和指标，避免只罗列框架名。

#### （2）多轮对话中的状态应该怎样管理？

把不可变的原始事件、当前会话工作状态和可检索的长期记忆分开。原始事件用于审计与重放；检查点保存任务阶段、工具结果和幂等键；模型可见上下文则按 Token 预算动态装配。进程重启后应从持久化检查点恢复，而不是依赖内存聊天记录。

延伸阅读：[Agent 会话、检查点与任务状态存储](../../../knowledge/backend/storage/agent-state-storage.md)、[Agent 记忆系统架构设计](../../../knowledge/llm/agent/agent-memory-architecture.md)。

#### （3）ReAct 循环的输入输出契约应该怎样设计？

每轮输入至少包含目标、当前状态、可用工具、预算和上轮结果；输出应是可校验的结构化动作或最终答案。运行时负责校验、执行和记录事件，模型不直接控制重试次数或权限。还要设置最大步数、总时限和“进展判定”，防止循环空转。

延伸阅读：[ReAct：推理与行动框架](../../../knowledge/llm/agent/agent-react.md)。

#### （4）模型返回非法 Tool Call 或错误参数时怎么办？

先在适配层做 JSON Schema、类型、枚举和业务约束校验。可修复的参数错误把精确错误反馈给模型并限制重试次数；权限错误和不可恢复错误立即终止或转人工；有副作用的工具用幂等键和状态查询避免重复执行。不要在解析失败后静默猜参数。

延伸阅读：[工具结果校验、解析与反馈](../../../knowledge/llm/agent/agent-tool-result-validation.md)。

#### （5）多 Agent 怎样通信？子 Agent 超时或宕机怎样兜底？

短任务可同步调用，长任务使用队列或事件。消息需携带 run/task ID、Schema 版本、deadline、幂等键和状态引用；共享状态要明确字段所有者。子 Agent 失败后先按错误类型决定重试、降级为确定性工具、跳过非关键分支或转人工，父任务应能给出部分成功结果。

延伸阅读：[多智能体消息、协议与状态同步](../../../knowledge/llm/agent/agent-multi-agent-messaging.md)、[失败分类、重试、补偿与恢复](../../../knowledge/llm/production/agent-failure-recovery.md)。

#### （6）怎样避免 Agent 在长对话中忘记用户的核心意图？

把目标、约束和已确认决策保存为结构化任务状态，而不是只依赖历史消息。每次行动前重新注入当前目标；摘要时对关键约束使用独立字段和版本号，出现冲突则以用户最新明确指令为准，并保留变更记录。

#### （7）“总结文章并发送到群里”的完整链路是什么？

先取得文章读取权限并解析正文，生成带来源依据的摘要，再确认目标群、消息格式和发送权限。发送属于外部副作用，应在执行前展示预览并获得确认，使用幂等键记录发送状态；超时后先查询结果再决定是否重试，避免重复发消息。

#### （8）怎样控制 Agent 的 Token、延迟与模型成本？

从减少无效上下文开始：裁剪工具结果、按需加载 Skill、缓存稳定结果、限制循环预算。随后按任务难度做模型路由，让小模型处理分类和抽取，把复杂规划交给强模型。用“单次成功任务成本”而非单次调用价格衡量优化，防止便宜模型因重试反而更贵。

延伸阅读：[Token、延迟与成本优化](../../../knowledge/llm/production/llm-cost-optimize.md)。

#### （9）Agent 效果评测应该包含哪些指标？

结果层关注任务成功率、答案正确性和业务完成率；过程层关注工具选择、参数正确率、无效步骤、Token、延迟和失败恢复；安全层关注越权和危险动作。离线使用版本化测试集做回归，线上结合抽样审核、用户反馈和真实失败案例，分场景报告而不是只给总平均分。

延伸阅读：[智能体性能评估](../../../knowledge/llm/agent/agent-evaluation.md)。

#### （10）长短期记忆和摘要压缩怎样配合？

短期记忆服务当前任务，保留最近对话、计划和工具结果；长期记忆只存跨会话仍有价值、且经过确认的事实与偏好。接近上下文预算时触发摘要，摘要需保留目标、约束、未完成事项和关键证据，并通过原始事件引用支持追溯。

延伸阅读：[会话摘要、压缩与记忆提炼](../../../knowledge/llm/agent/agent-memory-summarization.md)。

#### （11）带超时控制的工具调用怎样实现？

为单次调用设置可取消的 deadline，并把剩余预算传给下游。超时后区分“确定未执行”和“结果未知”：前者可对幂等操作做指数退避重试，后者必须用 operation ID 查询状态。重试耗尽后返回结构化错误并执行降级策略。

延伸阅读：[工具超时、取消与重试](../../../knowledge/llm/agent/agent-tool-timeout.md)。

#### （12）LangChain、LangGraph 和自研框架怎样选？

线性原型可用轻量 SDK；需要显式状态、分支、检查点和人工接管时，图式编排更合适；只有在性能、合规或运行语义确有特殊要求时才自研。选型要用可观测性、恢复能力、测试性、升级成本和团队熟悉度解释，而不是比较功能清单。

#### （13）怎样阻止 Agent 重复调用同一个工具？

运行时记录规范化后的“工具名 + 参数 + 关键状态”指纹；相同状态下重复调用达到阈值就阻断。再结合最大步数、无进展检测、成本预算和终止原因分类，让系统可以停止、换策略或转人工，而不是继续提示模型“再想想”。
