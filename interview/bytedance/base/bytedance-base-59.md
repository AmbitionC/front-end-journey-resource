<details data-knowledge-key="ai-observability">
<summary>（1）复盘实习项目的不足时，怎样用失败样例与指标确定优化点？</summary>
</details>

先用真实失败样例和同负载指标说明问题，再拆开排队、检索、模型、工具与重试耗时，选择一个主要变量改动。比较质量、失败率、延迟和成本，保留回滚条件；只讲自己能提供证据的改进，不能编造项目规模、优化比例或线上结果。

<details data-knowledge-key="prompt-testing-debugging">
<summary>（2）模型输出不符合指令时，怎样定位原因并验证改进？</summary>
</details>

保存脱敏输入、实际组装的指令与版本、工具结果和原始输出，先区分指令缺失或冲突、上下文缺失、格式错误与事实错误。例如一个教学假设：要求只输出含 status 的 JSON，实际却带 Markdown 围栏；可用解析与字段校验复现，若发现格式要求冲突再消除冲突，修订后用原失败样例和未参与调试的样例回归。这不是原作者的实际案例，一次回答变好也不等于稳定解决。

<details data-knowledge-key="llm-long-context">
<summary>（3）Cursor 长上下文出现性能下降时，怎样验证原因并处理？</summary>
</details>

先固定工具与模型版本及任务，比较输入规模、模型首 Token 延迟（从发送模型请求到收到首个输出 Token）、总耗时和结果质量，区分上下文增大、工具等待与其他瓶颈。确认上下文是主因后，按当前目标保留必要代码、约束和证据，裁剪无关历史，摘要保留来源和未完事项，再检查正确性是否退化；不凭一次体验推断 Cursor 的固定内部架构或通用长度阈值。
