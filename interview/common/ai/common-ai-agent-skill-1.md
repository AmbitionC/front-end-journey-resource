> 题源：牛客网公开讨论帖（AI 面试题题解专题）。原帖只列题目、未给答案，下列解答由本站整理补齐。

### 面试中的问题：

#### （1）描述 Skill 热插拔的流程

热插拔指**不重启 Agent、不改动其它 Skill，就能新增/更新/下线一个 Skill**。典型流程：

1. **发现**：扫描 skill 目录或注册中心，读取每个 Skill 的清单（名称、描述、版本、入口、依赖）。
2. **校验**：schema 校验清单，检查 name 唯一、版本合法、依赖可满足；不合法的直接拒绝装载，不影响现有 Skill。
3. **注册**：把「名称 + 描述」这类**元信息**写进路由索引（便宜、常驻），正文与脚本先不加载。
4. **生效**：路由层原子替换索引条目（新旧版本切换要么全成功要么回滚），进行中的任务继续用旧版本，新任务用新版本。
5. **卸载**：从索引移除并释放资源；有引用计数时等待在途任务结束（优雅下线）。

关键点是**索引与正文分离**：热插拔只动索引，正文按需加载，所以代价小、可回滚。

#### （2）解释 RAG、Skill、MCP

三者常被混谈，但解决的是不同层面的问题：

+ **RAG（检索增强生成）**：解决「**模型不知道你的私域事实**」。把问题向量化 → 从语料库召回相关片段 → 拼进上下文再生成，用检索到的事实做接地（grounding），降低幻觉。
+ **Skill**：解决「**模型不知道该怎么做这类任务**」。是一份可被按需加载的「做事说明书」（说明 + 可选脚本/资源），把领域流程、规范、边界固化下来复用。
+ **MCP（Model Context Protocol）**：解决「**模型怎么够得着外部工具与数据**」。是一套标准协议，让模型/宿主以统一方式发现并调用外部 server 暴露的工具与资源。

一句话：**MCP 管「怎么连」，Skill 管「怎么做」，RAG 管「拿什么事实」**。三者可叠加：一个 Skill 里可以规定「先用 RAG 查规范，再用某个 MCP 工具落库」。

#### （3）Skill 优先加载什么？渐进式披露加载是什么？

**优先加载元信息**：启动时只把每个 Skill 的 `name` + `description`（几十个 token）装进上下文，作为「目录」；正文、示例、脚本、附件都不加载。

**渐进式披露（progressive disclosure）** 就是把加载拆成层次，用多少读多少：

1. 第一层：名称 + 描述 → 供模型判断「这次要不要用它」。
2. 第二层：命中后加载完整说明书正文（步骤、规范、注意事项）。
3. 第三层：正文里引用的参考文件 / 脚本，真正需要时才读取或执行。

好处是**上下文预算与 Skill 数量解耦**：挂 100 个 Skill，常驻开销仍只是 100 条描述，而不是 100 篇正文。

#### （4）Skill 路由评测怎么设计

把「选对 Skill」当成一个**分类/检索问题**来评测：

+ **数据集**：收集真实请求，标注 golden skill（含「不该用任何 Skill」的负样本），覆盖易混淆对（如两个相似 Skill）。
+ **指标**：Top-1 准确率、Recall@k、F1；负样本上的**误触发率**要单独看。
+ **切分**：按场景/时间切分，避免过拟合；难例（近义、跨领域）单独成集。
+ **回归**：每次改描述、加新 Skill 都跑一遍，防止「新增一个 Skill 打乱既有路由」。
+ **归因**：错误分桶（描述写得差 / 语义太近 / 缺负样本 / 检索召回不到），指导下一步改哪里。

评测的关键是**把 Skill 描述当作可迭代的产物**——多数路由问题最终都能回到描述写得不够判别性。

#### （5）命中率不佳，但只能命中一个 Skill、且不能改 Skill 本身，怎么办？

约束是「Skill 不可变 + 只能选一个」，那就只能在**选择层**做文章：

+ **换召回方式**：从关键词匹配升级为向量召回，或两段式「向量粗排 → 精排/LLM 择一」。
+ **给路由器补上下文**：加入 few-shot 路由样例、类目先验、用户/场景特征；对历史命中做统计先验。
+ **加中间层**：先做意图分类到大类，再在类内选 Skill，缩小候选集。
+ **调阈值与兜底**：置信度低于阈值时走「不使用 Skill」的默认路径，避免错触发比不触发更糟。
+ **用检索侧的别名/同义扩展**：在索引层（不改 Skill）挂关键词别名，改善召回。

本质是：**不能改被选项，就改选择器和候选集构造方式**。

#### （6）Agent 的 Skill 怎么理解？

可以理解为**给 Agent 的「岗位 SOP」**：不是一次性的提示词，而是可复用、可版本化、可按需加载的能力封装。它通常包含做事步骤与判断标准、适用与不适用边界、可选的脚本/模板/参考资料。

与「把所有规则塞进 System Prompt」相比，Skill 的价值在于**按需加载**（省上下文）、**独立演进**（各自版本化）、**可组合**（不同任务装配不同 Skill）。

#### （7）Skill 与传统提示词工程、MCP 三者的差异？

+ **提示词工程**：作用于**单次请求**的措辞与结构，通常内联、全量常驻，难以规模化管理。
+ **Skill**：作用于**一类任务**的做法沉淀，可按需加载、可版本化、可复用，是「被管理起来的提示词 + 资源」。
+ **MCP**：作用于**连接**，标准化工具/资源的发现与调用，不规定业务怎么做。

递进关系：提示词工程解决「这一句怎么说」，Skill 解决「这类事怎么做且能复用」，MCP 解决「要用的外部能力怎么接进来」。

#### （8）如何给 Agent 工具系统设计动态 Skill，而不让版本升级破坏历史任务？

核心是**不可变版本 + 显式绑定**：

+ Skill 用语义化版本，**已发布版本不可变**；升级即发布新版本而非原地覆盖。
+ 任务在开始时**记录所用 Skill 的 id@version**，运行中始终用该版本（pin），保证可复现与可回放。
+ 保持**向后兼容契约**：name、描述语义、输入/输出结构不随意改；破坏性变更升 major 并保留旧版一段时间。
+ **灰度与回滚**：新版本按比例放量，指标异常可秒回退旧版本。
+ **回归测试**：升级前跑路由评测与端到端用例，确认既有场景不劣化。

#### （9）Skill 的依赖关系怎么解决？

+ 在清单里**显式声明依赖**（依赖的工具、其它 Skill、外部服务及版本范围）。
+ 装载时做**依赖解析与环检测**，缺依赖直接拒绝装载并给出清晰报错。
+ 依赖**按需加载**，避免启动即全量拉起。
+ 倾向**扁平、少依赖**的设计：Skill 之间尽量通过明确输入/输出协作，而不是深度耦合调用链。

#### （10）Agent 里的 Skill 到底怎么做才算高质量？

+ **描述具判别性**：一句话说清「什么时候用、什么时候不用」——这是路由准确率的最大杠杆。
+ **单一职责**：一个 Skill 只解决一类任务，避免大而全导致既难路由又难维护。
+ **步骤可执行**：给出明确流程与判断标准，而非笼统建议。
+ **边界清晰**：写明前置条件、不适用场景、失败时怎么办。
+ **可评测**：配套用例，能量化回答「它有没有变好」。
+ **上下文经济**：正文精炼，重资料放引用层按需读取。

#### （11）挂 100 个 Skill 时，如何提升召回率、准确度与 F1？

规模上来后，路由从「能选对」变成「检索问题」：

+ **两段式路由**：向量召回 Top-k（保召回）→ 精排或 LLM 择一（保准确），兼顾 F1。
+ **优化索引文本**：用「描述 + 典型场景 + 反例」构建索引条目，而不是只用名字。
+ **分层/命名空间**：先按领域分类再类内选择，天然降低候选混淆。
+ **负样本与阈值**：显式训练/校准「不该命中」的情况，压低误触发。
+ **聚类去重**：把语义高度重叠的 Skill 合并，重叠本身就是路由错误之源。
+ **持续评测驱动**：以 F1 为目标做 A/B，逐条修描述、补样例。

#### （12）React 里的「skill」与库是怎么运转的？

原帖此问表述不完整（React 生态并无标准的「Skill」概念）。若指**在 React 应用里接入 Agent Skill**，通常是：前端只负责会话与工具调用的 UI 呈现（消息流、工具调用状态、审批确认），Skill 的装载与路由发生在服务端 Agent 运行时；前端通过流式接口订阅事件并渲染。若指**组件库的按需加载**，那对应的是打包层的 code splitting 与 tree shaking，与 Agent Skill 不是同一层概念。
