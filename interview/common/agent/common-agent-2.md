## 架构设计与模型接入

<details data-knowledge-key="agent-coding"><summary>（1）让我先整体介绍一下本地Coding Agent项目，从输入任务到最终修改代码，中间完整链路是怎样的？</summary></details>
<p>可以沿“任务与验收标准、仓库基线、相关代码检索、计划、受控工具执行、测试与 Diff 审查”讲完整链路。模型负责提出下一步动作，运行时校验权限、参数、预算并保存结果；只有产物和验证满足标准才结束，不能把模型说完成当成功。</p>

<details data-knowledge-key="llm-api-basics"><summary>（2）Agent支持不同模型后端吗？如果接入多个模型服务，怎么抽象请求格式、响应结构、错误码和重试逻辑？</summary></details>
<p>我会用统一请求和响应合同隔离供应商差异，再为每个后端实现适配器和能力声明。合同保留内容块、工具调用、结束状态、用量及追踪信息，错误归一分类但保留原始码；只有可恢复且满足幂等条件的失败才在总预算内重试，并用契约测试检查兼容性。</p>

<details data-knowledge-key="build-agent-framework"><summary>（3）怎么理解Agent Harness？它和单纯调用LLM API的本质区别是什么？</summary></details>
<p>Harness 是让模型持续完成任务的运行支撑，包括上下文装配、工具编排、状态与恢复、权限、预算和终态验收。单次调用 LLM API 只产生一次候选输出，Harness 还要把动作安全执行、收回观察并决定继续或停止；评测的也是模型与这套运行支撑的组合。</p>

## 工具系统与容错机制

<details data-knowledge-key="agent-tool-design"><summary>（4）项目里的工具系统是怎么做的？比如一个新工具从定义、注册、被Agent发现，到最后被调用，完整流程是什么？</summary></details>
<p>先为工具定义窄而明确的意图、输入输出 Schema、权限、副作用和错误合同，再把实现与版本注册到运行时。Agent 发现的是当前主体可用的工具描述；真正调用前仍由执行端校验参数、授权、超时和幂等要求，结果再带调用标识回写状态，工具可见性不等于授权。</p>

<details data-knowledge-key="agent-failure-recovery"><summary>（5）如果工具调用失败（比如文件不存在、命令超时、权限不够），Agent是直接报错，还是会做恢复和重试？</summary></details>
<p>先把失败分成参数或资源问题、瞬态故障、权限拒绝和副作用状态未知，再决定恢复方式。文件不存在时核对路径与当前版本，瞬态故障按期限有界退避，权限不足则停止或升级；命令超时后先确认进程和已发生的效果，不能无条件重跑。</p>

<details data-knowledge-key="agent-coding"><summary>（6）如果Agent在执行代码修改时生成了错误patch，怎么做回滚、验证和再尝试？</summary></details>
<p>修改前记录 HEAD、未提交改动和本次补丁范围，优先在隔离工作区建立可恢复检查点。补丁失败先重新读取当前文件并核对前置版本；已应用但验证失败时，只撤销本次可确认的修改，再根据错误生成新补丁并重跑相关验证，不能用整库硬重置覆盖用户工作。</p>

## 上下文治理与记忆管理

<details data-knowledge-key="prompt-context-compression"><summary>（7）提到做了多轮任务中的上下文治理，举个真实场景？比如代码改到一半上下文越来越长，怎么处理的？</summary></details>
<p>这题需要用自己的真实任务说明；例如跨文件修改只是教学场景，不能当成实际经历。上下文变长时先移出可回读的大日志和重复结果，保留目标、约束、文件版本、已改内容、测试证据及下一步，并在继续前对照当前仓库确认摘要仍有效。</p>

<details data-knowledge-key="prompt-context-compression"><summary>（8）上下文压缩之后，怎么判断压缩没有破坏当前任务？有没有校验标准？</summary></details>
<p>我会把关键约束与事实列成保真清单，检查摘要是否保留否定条件、版本、未完成项、权限和工具结果状态，且能回到原始证据。再用同一组续跑任务比较压缩前后的约束遵守和最终成功率，同时计入摘要与重试成本；摘要看起来流畅或压缩率高都不足以验收。</p>

<details data-knowledge-key="prompt-context-compression"><summary>（9）任务摘要、文件摘要、过程笔记这些压缩产物，怎么生成和维护的？如何避免关键信息被压掉？</summary></details>
<p>任务摘要保存目标、约束、当前进展和下一步，文件摘要保存职责、接口及其源码版本，过程笔记保存决策、工具结果和证据位置。按变更或里程碑增量维护，并保留原始记录；更新时核对覆盖范围和基准版本，避免摘要套摘要累积漂移，精确 Diff 与错误日志优先保存引用。</p>

<details data-knowledge-key="prompt-context-compression"><summary>（10）如果压缩后的摘要遗漏了关键约束，导致后续Agent做错了，怎么发现并修正？</summary></details>
<p>先用约束清单、测试失败和 Diff 审查发现偏差，再回读原始指令与证据确认遗漏。暂停依赖错误摘要的后续动作，修正摘要并使受影响结论失效，从仍可信的检查点重新规划和验证；已经发生的修改或外部副作用要分别核对，不能把改好摘要当成任务已恢复。</p>

<details data-knowledge-key="agent-memory-poisoning"><summary>（11）如果长期记忆里保存了过时的文件摘要，后面Agent又拿它做判断，这种污染怎么处理？</summary></details>
<p>文件摘要应绑定仓库、路径、commit 或内容指纹，召回时先核对当前代码与有效期，旧摘要只作为定位线索。发现过期就停止用它决策，回读源码重建，并同步失效相关索引、缓存和派生摘要；重要修改前仍核验现有实现，不能用记忆替代源码。</p>

<details data-knowledge-key="agent-memory-poisoning"><summary>（12）如果模型把错误结论写进了记忆（比如误判某个函数作用），后续任务一直沿用，怎么做纠错？</summary></details>
<p>先回到对应版本的源码、调用方和测试验证函数语义，把未经验证的模型推断与事实分开。确认错误后撤销旧结论，保留更正依据与版本，并沿来源关系清理依赖它的摘要、缓存和共享副本；最后加入回归用例，检查后续检索和任务不会继续沿用旧结论。</p>

<details data-knowledge-key="agent-run-loop"><summary>（13）多轮执行中，Agent可能反复读同一个文件或重复调用同一个工具，怎么识别这种重复状态？</summary></details>
<p>为工具名、归一化参数、资源版本、返回结果和未完成目标计算进展指纹，连续重复且没有新增证据时触发无进展保护。分页、轮询和合法重试要把游标、等待时间、尝试次数纳入状态，避免误杀；超过任务阈值后换方法、补信息或停止，并保留轨迹。</p>

<details data-knowledge-key="context-engineering"><summary>（14）怎么看RAG、Memory和Context Engineering？三者分别解决什么问题？在Coding Agent里是怎么配合的？</summary></details>
<p>RAG 负责按任务从外部材料检索证据，Memory 保存可跨轮次或会话复用且有来源与有效期的状态，上下文工程决定本轮实际装入哪些指令、工具、证据和历史。在 Coding Agent 中可以检索当前版本代码、召回已验证的项目约定，再按权限、时效和预算装配；召回命中并不代表事实正确。</p>

## 评测体系与复杂场景

<details data-knowledge-key="agent-eval-framework"><summary>（15）Agent有没有评测体系？怎么设计benchmark、case、指标？怎么判断一次改动真的让Agent变强了？</summary></details>
<p>先把真实需求和故障整理成固定初始环境、允许动作与成功判据的用例，再用独立测试读取最终产物，并结合轨迹检查约束。比较改动时固定模型、工具、仓库和评分版本，重复运行并按任务切片报告成功率、回归、越权、延迟和每成功任务成本；另保留未参与调优的样本，避免只优化总分。</p>

<details data-knowledge-key="agent-coding"><summary>（16）如果Agent需要在一个大型代码仓库里完成跨模块修改，怎么让它先理解架构，而不是一上来就乱改？会设计哪些检索、规划和验证步骤？</summary></details>
<p>先读项目说明、目录、入口、依赖与相关测试，沿符号定义、引用和调用链建立受影响模块的架构地图，所有结论绑定当前仓库快照。再列出接口、数据流、不变量、改动顺序和分层验收计划，小步修改并核对跨模块调用方；类型检查、相关单元与集成测试及最终 Diff 都要有实际结果。</p>

<details data-knowledge-key="agent-permission-model"><summary>（17）如果把本地Coding Agent做成团队内部工具，怎么处理权限、安全和审计？比如文件读写、命令执行、敏感信息泄露。</summary></details>
<p>把团队身份、任务和目标资源带到每次工具授权，分别限制可读写目录、命令、网络、时间和预算，敏感凭据留在受控执行层。高风险操作按既有授权策略核对实际参数，执行前再次校验权限；审计记录主体、策略版本、调用、脱敏参数与结果，并验证租户隔离、撤销和秘密泄露路径。</p>

## 个人 AI 工作流

<details data-knowledge-key="agent-coding"><summary>（18）平时用什么AI？一个需求给到你，通常怎么用AI辅助完成开发？</summary></details>
<p>这里必须替换成自己的真实工具和案例，原帖没有给出可代填的个人经历。可以按需求澄清、代码理解、候选补丁、测试与 Review 说明各工具承担什么工作，再展示一次真实 Diff 和验证证据；本人要能解释取舍，提效结论需要同口径的实际比较。</p>

<details data-knowledge-key="agent-coding"><summary>（19）使用AI的过程中，怎么拆需求、读代码、让模型改代码、跑测试和review结果？</summary></details>
<p>先把需求写成可验收行为和改动边界，让 AI 搜索相关实现、调用方和测试，再审核可执行的修改计划。按小步骤生成补丁并运行必要测试，Review 时对照需求检查正确性、边界和无关改动；交付说明实际改了什么、验证结果及尚未验证的部分，不能只转述模型自评。</p>
