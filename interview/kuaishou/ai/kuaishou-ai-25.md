<details data-knowledge-key="redis-cache"><summary>（2）缓存击穿是什么，如何防范？</summary></details>
<p>缓存击穿通常指某个热点 key 失效时，大量并发请求一起回源数据库。可以按 key 合并重建，让一个请求加载，其他请求有截止时间地等待、读回填值或降级；取锁后再检查缓存，释放时原子校验所有权。允许短时旧值的业务也可采用逻辑过期并异步刷新，但要限制旧值最长寿命。TTL、等待时间和并发限制应按业务与负载选择，不能靠一把无期限锁或无限重试解决。</p>

<details data-knowledge-key="redis-cache"><summary>（3）缓存雪崩是什么？</summary></details>
<p>缓存雪崩是大量 key 集中失效，或缓存服务故障，使原本由缓存承接的请求大量回源，进而压垮数据库等下游。先区分集中到期和服务不可用：前者可分散 TTL、分批预热并限制重建并发；后者要有容量经过验证的高可用方案，以及超时、熔断、限流和按业务约定的降级。多级缓存只能在允许的旧值窗口内兜底，不能让故障时的所有请求无限直冲数据库，也不能把权限或余额校验随意交给旧缓存。</p>

<details data-knowledge-key="redis-distributed-lock"><summary>（4）详细讲讲你用的分布式锁是什么？</summary></details>
<p>原文没有给出作者实际使用的锁库，回答时应先说明自己的真实实现；以 Redis 租约为教学例，可用原子 SET key owner NX PX 获取带过期时间的锁，每次获取使用唯一 owner，释放时原子比较 owner 再删除，避免旧请求误删新锁。还需解释竞争等待上限、租约到期和续期失败、进程暂停及故障切换；安全释放只能保护锁键，不能阻止过期持有者继续写业务资源，关键写入仍需资源端版本或 fencing，以及合适的事务和幂等约束。</p>

<details data-knowledge-key="redis-distributed-lock"><summary>（5）Redis 实例只有一个，为什么需要分布式锁？分布式锁锁的是什么？</summary></details>
<p>Redis 实例数和业务竞争者数量是两件事：一个 Redis 仍可被多个服务进程或客户端共同访问，进程内锁不能跨这些进程协调。分布式锁通过所有参与者遵守的共享锁键，协调同一订单、任务或资源 ID 对应的业务临界区，并不是把整个 Redis 服务锁住；Redis 单条命令原子执行，也不能自动让“读数据库—判断—写数据库”的多步业务原子化。先证明存在跨进程竞争和所需不变量，再比较数据库唯一约束、条件更新或单消费者；若只有一个执行进程且没有外部竞争者，未必需要 Redis 锁，题目本身不能证明作者部署了几个服务实例。</p>

<details data-knowledge-key="logging-monitoring"><summary>（7）查某个日志文件中包含 error 的行数，写出命令。</summary></details>

<details data-knowledge-key="java-runtime-memory"><summary>（10）了解 Java 中的内存泄漏吗？</summary></details>
<p>Java 有 GC 仍会发生业务意义上的内存泄漏：已经无用途的对象被长期存活的引用链保留，仍然可达，GC 就不会把它当作垃圾。例如无界缓存、未清理的监听器或不当持有的 ThreadLocal 值都是排查候选，不能仅凭出现这些结构就定案。应在可比负载下观察回收后存活量的趋势，再用堆快照等证据检查保留路径并修正生命周期或容量；一次 OOM 或一次峰值不足以证明泄漏，文件句柄、连接和本地内存的释放也需按各自资源协议分析。</p>

<details data-knowledge-key="java-runtime-memory"><summary>（11）生产环境被描述为“栈占用 90% 以上”，且常发生栈溢出，你会如何分析和优化？</summary></details>
<p>先澄清“栈占用90%”的监控名称、分子分母、时间窗，以及是单线程还是全线程、保留还是提交内存，不能把未定义指标当作正常现象或根因。若确为 StackOverflowError，从完整异常栈和复现请求检查重复调用帧、递归终止条件与合法调用深度，必要时结合有影响评估的线程栈采样；修复错误递归，或把已确认过深的合法递归改成迭代并限制输入。再核对实际 -Xss、线程数与本地内存预算，评测后才调整容量；调大栈不能修复无界递归，GC 也不能解决调用深度，若实际是 OOM 则按对应内存区域另行取证。</p>

<details data-knowledge-key="garbage-collection"><summary>（12）详细讲讲垃圾回收机制。</summary></details>
<p>垃圾回收按运行时能追踪的引用关系识别可回收对象：追踪式回收从根集合标记存活对象，再清扫不可达对象的空间，或通过复制、压缩移动存活对象并更新引用；根不可达的对象环不必导致泄漏。分代利用对象生命周期差异，并行、并发和增量描述不同工作安排，不能混成一个固定算法。放到 Java，要先说明 JDK、JVM 和具体收集器，JVMS 没有规定唯一 GC 算法；实际策略在吞吐、暂停和内存间取舍，并发也不保证完全无暂停，仍可达但业务不用的对象与外部资源关闭还需应用管理。</p>
