<details data-knowledge-key="redis-cache"><summary>（2）本地缓存、Redis 与 MySQL 之间如何保持一致性？分布式场景要考虑什么？</summary></details>
<p>先说明数据库保存权威事实，本地缓存与 Redis 分别允许怎样的旧值窗口，再沿读、写和失效路径展开。写数据库后失效 Redis 还需处理各进程的本地副本、通知断线、删除失败与旧请求晚回填，结合版本、失效补偿和 TTL 约束风险。付款或权限等关键判断仍在权威事务中校验，不能把通知或双删称为跨层强一致。</p>

<details data-knowledge-key="redis-cache"><summary>（3）如何避免 Redis 缓存击穿，并处理 Redis 与 MySQL 的数据一致性？</summary></details>
<p>先把热点 key 同时失效造成的击穿，与不存在数据的穿透区分开，再用并发请求合并、互斥重建或有边界的旧值返回限制回源。重建要有超时、降级和版本检查，租约到期后的旧请求不能继续无条件覆盖新值。数据库提交与缓存失效之间仍有失败窗口，应配合可重试失效与业务允许的旧值合同。</p>

<details data-knowledge-key="os-deadlock"><summary>（4）哪些情况会形成死锁？</summary></details>
<p>从资源和等待关系出发，说明互斥、持有并等待、不可剥夺与循环等待这四个必要条件，并区别普通等待、死锁与活锁。统一获取顺序可以阻断相应锁集合的循环等待，检测后则需选择可恢复的执行单元回滚。超时本身不是无死锁证明，获取失败后还要释放已持资源并有界退避。</p>

<details data-knowledge-key="db-transaction-lock"><summary>（5）MySQL 可能在什么情况下发生死锁，怎样处理？</summary></details>
<p>先限定存储引擎、SQL、索引与事务边界；以 InnoDB 为例，事务以不同顺序持有和请求冲突记录锁时可能形成等待环，单行操作也可能涉及多个索引记录。结合最近死锁记录和锁等待信息定位，再通过一致访问顺序、缩短事务及合适索引降低发生概率。死锁回滚后按业务幂等边界有界重试整个事务，并与锁等待超时的回滚范围区分。</p>

<details data-knowledge-key="redis-cache"><summary>（6）Bloom 过滤器的原理是什么，怎样实现？</summary></details>
<p>布隆过滤器用位数组和多个散列位置记录成员；正确加入元素且未错误清位时，查询任一位置为零可判其不在所维护的集合，全为一只表示可能存在。容量、哈希数量与目标假阳性率共同影响空间和计算代价，标准结构不能直接删除单个元素的共享位。用于缓存前置过滤时，还要保证装载和新增同步，覆盖未确认时不能直接拒绝真实请求。</p>

<details data-knowledge-key="redis-distributed-lock"><summary>（7）分布式锁如何实现，有哪些关键边界？</summary></details>
<p>先说明需要协调的共享资源，以及能否用唯一约束、条件更新或单消费者解决，再以 Redis 租约作为一种实现展开。原子获取要带唯一持有者标识与过期时间，释放和续期均需核对所有权，并限制等待与重试。进程暂停、租约失效和故障切换仍可能破坏互斥，重要写入还需资源端版本或 fencing，不能仅凭加锁承诺业务只执行一次。</p>
