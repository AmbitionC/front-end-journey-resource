软件工程基础题主要在考“按什么维度分类”：生命周期模型组织开发活动，UML 从不同视角描述系统，测试技术说明怎样选用例，测试层次说明正在验证哪个范围。把这几条轴分开，才能避免“白盒就是单元测试”“V 模型必须写完代码才考虑测试”等混淆。本文面向银行、国企科技岗基础复习，全部练习均为原创模拟题，不对应或预测任何单位的真实试卷。

## 生命周期模型：先识别它主要控制什么

生命周期模型是对开发活动及其关系的抽象，并不表示一个名称就能决定项目的所有实践。以下按常见教学模型比较：

| 模型或组织方式 | 最应抓住的特点 | 判断边界 |
| --- | --- | --- |
| 瀑布模型 | 需求、设计、实现、测试等阶段有较明确的先后和交付关系 | 不能推出绝不允许反馈或返工；需求变化可能造成跨阶段返工 |
| 增量开发 | 把可交付能力分成若干部分，逐步增加功能 | 每个增量仍需分析、设计和测试，不是先写全部代码再分批交付 |
| 迭代开发 | 重复开展活动，依据反馈修正、细化已有方案或实现 | 迭代强调反复改进，增量强调能力增加，二者可以同时存在 |
| 螺旋模型 | 由风险决定下一轮做什么、怎样验证、投入多少 | “重复几轮瀑布”不足以构成螺旋模型的核心特征 |
| V 模型 | 开发工作产品与对应测试建立可追溯关系 | 测试分析和设计应尽早开始，不能只看右侧的执行阶段 |

顺序、迭代和增量模型的分类及其对测试的影响参阅 [ISTQB CTFL v4.0.1，第 2.1 节](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)。瀑布模型中的反馈与返工也可核对 [CMU 18-642《Software Development Processes》](https://users.ece.cmu.edu/~koopman/lectures/ece642/03_SoftwareProcess.pdf)；螺旋模型的风险驱动含义依据 [CMU/SEI 的螺旋开发报告](https://www.sei.cmu.edu/library/spiral-development-experience-principles-and-refinements-spiral-development-workshop-february-9-2000/)。

用一个小例子区分增量与迭代：第一版可查询余额，第二版新增转账，是能力上的增量；依据首版反馈重新设计查询界面，是对已有能力的迭代。若第二版同时做了这两件事，它就是既增量又迭代，两个术语不互斥。

### 原创模拟题 1：先做原型是在解决什么

某项目对人脸核验算法的准确率和现有终端性能没有把握。团队在每轮开始时分析主要风险，先做原型或实验消减风险，再决定后续方案与投入。最符合哪种模型的核心特点？

- A. 瀑布模型，因为所有原型都必须在需求冻结后进行
- B. 螺旋模型，因为下一步活动由风险评估驱动
- C. V 模型，因为它只要求最终验收一次
- D. 增量开发，因为只要代码分几次提交就是增量

**答案：B。** 题干的决定性线索是“识别风险、通过实验消减风险、据此选择下一步”。原型本身并非螺旋模型专属，但在本题中它服务于风险决策。A 给瀑布加了不成立的绝对条件；C 错解 V 模型；D 把版本管理中的提交粒度当作可交付能力的增量。

## V 模型：左右两侧为什么要对应

需求说“系统应完成什么”，设计说“怎样由各部分协作实现”，测试再根据相应依据验证结果。下图采用常见的四层教学映射：用户或业务需求对应验收测试，系统需求与规格对应系统测试，架构设计对应集成测试，模块详细设计对应单元测试。它用于解释追溯关系，不要求所有项目使用完全相同的阶段名称。[CMU 18-642：V 开发周期与测试依据](https://users.ece.cmu.edu/~koopman/lectures/ece642/03_SoftwareProcess.pdf)

![V 模型教学映射：业务需求对应验收测试，系统规格对应系统测试，架构对应集成测试，模块设计对应单元测试，编码位于底部；虚线标出测试依据](https://font-end-journey-resources.oss-cn-hangzhou.aliyuncs.com/images/soe-software-engineering-mcq-v-model-v1.png)
*图：实线表示开发与测试的教学展开顺序，虚线表示测试依据；测试分析、设计和静态评审可以早于编码完成，实际项目可能另分系统集成测试。*

横向对应的含义是“左侧工作产品帮助确定右侧测什么、怎样判定结果”。在需求草稿形成时就可以讨论验收标准，在模块设计时就可以设计单元测试；代码可执行之后再运行相应动态测试。左侧也能进行评审等静态测试，所以不能把 V 的左侧理解成“没有测试”。[CMU/SEI：Using V Models for Testing](https://sei.cmu.edu/blog/using-v-models-for-testing/)

V 模型是教学抽象。真实项目可以在多个迭代中重复这些活动，测试层次也可能在时间上交叠；对于外部系统接口，还可单独设置系统集成测试。做题时优先按题干的测试对象和依据判断。

## UML：先选视角，再读符号

UML 是建模语言，不是某一种开发流程，也不等于自动生成代码的工具。UML 2.5.1 将图分为结构图和行为图；交互图属于行为图。下面按 [OMG UML 2.5.1，附录 A 与第 17.1.4 节](https://www.omg.org/spec/UML/2.5.1/PDF)整理常见的 14 种图。

| 大类 | 图 | 主要回答的问题 |
| --- | --- | --- |
| 结构 | 类图 Class | 有哪些类、属性、操作及类之间的关系？ |
| 结构 | 对象图 Object | 一组对象实例及其链接是什么样子？ |
| 结构 | 包图 Package | 模型元素怎样分组，包之间怎样依赖？ |
| 结构 | 组件图 Component | 系统由哪些组件组成，提供和需要哪些接口？ |
| 结构 | 部署图 Deployment | 软件制品部署到哪些运行节点或执行环境？ |
| 结构 | 组合结构图 Composite Structure | 某分类器内部的部件、端口、连接器怎样协作？ |
| 结构 | 剖面图 Profile | 如何用构造型等机制表达特定领域的建模约定？ |
| 行为 | 用例图 Use Case | 哪些参与者通过哪些用例与系统交互、达成目标？ |
| 行为 | 活动图 Activity | 动作、分支、并发和控制流、数据流如何展开？ |
| 行为 | 状态机图 State Machine | 一个对象在事件、条件作用下怎样转换状态？ |
| 行为／交互 | 顺序图 Sequence | 多条生命线之间按什么先后交换消息？ |
| 行为／交互 | 通信图 Communication | 交互参与者怎样连接，用消息编号表达什么顺序？ |
| 行为／交互 | 交互概览图 Interaction Overview | 多段交互之间的控制流程怎样组织？ |
| 行为／交互 | 定时图 Timing | 状态或条件沿时间轴怎样变化？ |

其中 Profile Diagram 常译为“剖面图”或“轮廓图”；它不是表示软件文件的 Artifact。这里把它列入完整图分类，做题时应以英文名称和所描述的对象为准。部署图中的 Artifact 才是软件制品。

相同系统可以同时拥有类图、顺序图和部署图；这些图描述不同方面，不能从“都画了对象和线”推断它们等价。活动图关注活动流，状态机图关注对象在事件下的状态变化；顺序图与通信图都描述交互，但组织视角不同。

### 原创模拟题 2：为三个问题选择合适的图

现需分别表达：①转账请求在界面、服务、风控组件间的消息先后；②账户由正常变为冻结、再解冻的事件和条件；③应用制品部署在哪些服务器节点上。最合适的对应关系是哪项？

- A. ①类图，②部署图，③活动图
- B. ①顺序图，②状态机图，③部署图
- C. ①对象图，②包图，③用例图
- D. ①部署图，②顺序图，③状态机图

**答案：B。** ①以参与者的消息顺序为中心，选顺序图；②以账户状态及触发条件为中心，选状态机图；③以执行环境和制品分配为中心，选部署图。其他选项都把描述维度混在了一起。

### 关系的箭头、三角和菱形放在哪一端

下面先给常用含义，再给读图方向。类图中的多重性也要单独读，省略多重性不能自动推断成“一对一”。

| 关系 | 常见记号与方向 | 应怎样理解 |
| --- | --- | --- |
| 关联 Association | 实线，可附角色、多重性和导航性 | 表达实例之间的关联；不能仅凭实线推出对象的生存期 |
| 依赖 Dependency | 虚线箭头，使用方／客户指向被依赖方／供应者 | 一方的定义或实现需要另一方；不等于对象之间必有长期持有关系 |
| 泛化 Generalization | 实线、空心三角指向一般分类器 | 特殊类型与一般类型的关系，如子类指向父类 |
| 实现 Realization | 虚线、三角箭头指向被实现的规格 | 实现者满足规格；类实现接口是常见例子 |
| 共享聚合 Shared Aggregation | 关联线的整体一端为空心菱形 | 表达聚合；UML 不为所有领域统一规定更强的共享聚合语义 |
| 组合 Composite Aggregation | 整体一端为实心菱形 | 部件对象同时至多属于一个组合对象；整体删除时，其仍拥有的部件对象随之删除 |

依赖与实现依据 [UML 2.5.1 第 7.7 节](https://www.omg.org/spec/UML/2.5.1/PDF)，泛化依据第 9.2 节；聚合、组合及记号依据第 9.5、11.5 节。组合部件若按模型允许的操作提前移出，可以不随原整体删除，因此不能把组合简化为“部件永远不能独立存在”。导航箭头、多重性和所有权也不是同一件事。

用例中还常考两种方向不同的虚线关系：

- `«include»`：从包含它的基础用例，指向被包含用例，表示复用、插入后者的行为。
- `«extend»`：从扩展用例，指向被扩展的基础用例，在约定扩展点补充行为，可带条件；基础用例不依赖扩展也有独立意义。

这两种关系的方向与含义依据 [UML 2.5.1 第 18.1.3、18.1.4 节](https://www.omg.org/spec/UML/2.5.1/PDF)。不能仅凭业务语言中的“包含”“扩展”两个字猜箭头，必须先分清哪个用例提供行为、哪个用例使用该行为。

### 原创模拟题 3：include 与 extend 的方向

“提交转账”每次都要执行公共的“核验身份”行为；“打印纸质回执”仅在用户选择时，在“提交转账”定义的扩展点补充，未选择也能完整完成转账。哪项建模正确？

- A. 核验身份 `—«include»→` 提交转账；提交转账 `—«extend»→` 打印纸质回执
- B. 提交转账 `—«extend»→` 核验身份；打印纸质回执 `—«include»→` 提交转账
- C. 提交转账 `—«include»→` 核验身份；打印纸质回执 `—«extend»→` 提交转账
- D. 三者都必须使用泛化，且箭头指向打印纸质回执

**答案：C。** “提交转账”使用“核验身份”的公共行为，因此 include 指向核验身份；“打印纸质回执”是附加行为，因此 extend 从它指向基础用例。A 将两条关系都反向；B 混淆复用与扩展；D 没有题设支持的“一般类型／特殊类型”关系。

## 测试方法：设计依据与测试范围是两条轴

黑盒按规格、接口约束或业务规则选测试，白盒根据内部结构选测试，例如补齐尚未执行的分支；二者可以相互补充。判断依据是**如何设计用例**，不取决于测试者是否为开发人员，也不取决于是否使用自动化。[MIT 6.005：Blackbox and Whitebox Testing](https://ocw.mit.edu/ans7870/6/6.005/s16/classes/03-testing/)

静态测试与动态测试是另一条分类轴：前者不运行被测软件，例如评审需求、检查代码；后者执行被测软件并观察结果。不能把“静态＝白盒、动态＝黑盒”当作对应关系。[ISTQB CTFL v4.0.1，第 3.1 节](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)

### 等价类与边界：先划区域，再看交界

等价类划分先根据预期处理方式划分输入区域，再为每个区域选代表；这是降低测试数量的设计假设，不是“一次通过就数学证明整个区域无缺陷”。边界值分析用于有顺序的区域，重点检查端点和邻近值。[MIT 6.005：Choosing Test Cases by Partitioning](https://ocw.mit.edu/ans7870/6/6.005/s16/classes/03-testing/)、[ISTQB CTFL v4.0.1，第 4.2.1、4.2.2 节](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)

例如某字段只接受整数，规则为“小于 10 返回 LOW；10 到 60（含两端）返回 OK；大于 60 返回 HIGH”。可以划成三类，分别选 `9、35、61` 检查不同处理。若题目要求检查有效范围的端点及紧邻值，就要围绕 10、60 增选数据。

测试数据数量必须跟题干走：整数的前驱、后继是减一、加一；连续数值、字符串长度和日期则有各自的步长或邻近定义。资料也可能针对全部等价类边界指定二值或三值分析，不能把某一组“六个数”当作所有边界题的固定答案。

### 原创模拟题 4：按明确规则选边界值

沿用上述整数规则。题干现明确要求：**只针对有效区间的下端点 10、上端点 60，分别选“前驱、端点、后继”**。应选择哪组数据？

- A. `10、60`
- B. `9、10、11、59、60、61`
- C. `0、35、100`
- D. `9、35、61`

**答案：B。** 10 的前驱、端点、后继是 `9、10、11`；60 的对应值是 `59、60、61`。

A 只测两个端点，遗漏两侧邻近值；C、D 可以作为区域代表，但不满足本题指定的边界集合。本题没有把该集合宣称为“针对所有等价类边界的完整三值覆盖”，其范围已经在题干限定。

## 白盒覆盖：覆盖了什么，才是百分比的分母

覆盖率表示某类覆盖项有多少被执行，不能单凭一个“100%”比较测试强弱。

| 覆盖指标 | 要检查的覆盖项 |
| --- | --- |
| 语句覆盖 | 每条可执行语句是否至少执行一次，不是源码物理行数 |
| 判定覆盖 | 每个判定的各个结果是否出现，例如 if 的真、假 |
| 分支覆盖 | 控制流图的分支是否走到；包含条件与无条件控制转移 |
| 条件覆盖 | 每个原子条件是否分别取得真、假 |
| 条件／判定覆盖 | 同时满足原子条件结果与整体判定结果的要求 |
| 条件组合覆盖 | 检查判定中原子条件的真值组合；独立的 k 个布尔条件有 $2^k$ 种逻辑组合 |
| 路径覆盖 | 是否覆盖程序中的执行路径；循环可能带来无穷多条路径 |

语句、分支的定义与“100% 分支覆盖包含 100% 语句覆盖”依据 [ISTQB CTFL v4.0.1，第 4.3 节](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)。判定与原子条件的区分、条件组合以及短路影响参阅 [ISTQB CTAL-TTA v4.0，第 2.3—2.5、2.8 节](https://istqb.org/wp-content/uploads/2024/11/ISTQB-CTAL-TTA_Syllabus_v4.0.pdf)；路径覆盖还可核对 [MIT 6.005 的 Coverage 小节](https://ocw.mit.edu/ans7870/6/6.005/s16/classes/03-testing/)。

在通常控制流覆盖模型中，达到 100% 分支覆盖就包含 100% 语句覆盖，反向不成立。**条件覆盖与判定覆盖不能直接排成强弱等级**：原子条件分别变过真、假，整体判定仍可能始终为真；整体判定变过真、假，也未必让每个原子条件都变过真、假。下面两题用具体值验证，不依赖背诵口号。

此外，覆盖率不等于正确率。执行到有缺陷的语句，未必触发相应错误；触发错误后，也仍需正确的预期结果和断言才能识别它。不可达路径、耦合条件与具体覆盖工具的计数约定也会影响能否达到某个覆盖目标。

### 原创模拟题 5：语句全执行，是否已覆盖两个分支

考虑下列伪代码。语句覆盖只统计三条赋值或返回语句；判定覆盖只统计 if 判定的真、假两个结果。测试集只有 `x=2`。

```text
y = 0
if x > 0:
    y = 1
return y
```

“语句覆盖率；判定覆盖率”是哪项？

- A. `100%；100%`
- B. `50%；100%`
- C. `100%；50%`
- D. `50%；50%`

**答案：C。** 该测试依次执行 `y=0、y=1、return y`，三条全部覆盖；但 `x>0` 只出现真，没有出现假。没有 else 语句也不表示不存在假分支，假时会绕过 `y=1` 到达 return。

补充 `x=0` 就能让判定取假，但这仍只证明满足这里的覆盖目标，不能证明整个函数符合所有业务需求。

### 原创模拟题 6：条件都取过真和假，为何判定仍不全

考虑布尔表达式 `p OR q`。本题采用**非短路的逻辑模型**，每次都计算两个原子条件，且 p、q 无副作用。测试集为 `(p=true,q=false)` 与 `(p=false,q=true)`。下列哪项正确？

- A. 条件覆盖、判定覆盖都为 100%
- B. 条件覆盖为 100%，判定覆盖为 50%
- C. 条件覆盖为 50%，判定覆盖为 100%
- D. 两个指标都为 50%

**答案：B。**

| 用例 | p | q | 整体 p OR q |
| --- | --- | --- | --- |
| 1 | 真 | 假 | 真 |
| 2 | 假 | 真 | 真 |

p 和 q 都分别出现过真、假，四个原子条件结果全部覆盖；整体却只出现真，因此判定结果仅覆盖一半。这也没有达到条件组合覆盖：四种组合只测试了两种。

反方向同样不能推出：测试集若改为 `(真,假)` 与 `(假,假)`，整体 OR 分别为真、假，判定覆盖 100%，但 q 始终是假，条件覆盖只有 $3/4$。这两组反例都建立在“每个原子条件均被求值”的明确模型上。

### 原创模拟题 7：短路时，输入为真就等于执行过真吗

现改为从左到右短路求值的 `p && q`：p 为假就不再求值 q。输入明确为 `(p=true,q=false)` 与 `(p=false,q=true)`。条件覆盖只统计**实际求值**出现的原子条件真、假结果，不把未执行的 q 当作已经覆盖。条件覆盖率与判定覆盖率分别是多少？

- A. `100%；50%`
- B. `75%；100%`
- C. `75%；50%`
- D. `50%；100%`

**答案：C。**

| 输入 p、q | 实际求值 | 整体结果 |
| --- | --- | --- |
| 真、假 | p 为真，q 为假 | 假 |
| 假、真 | p 为假，q 未求值 | 假 |

原子条件结果总共四项：p 真、p 假、q 真、q 假。实际只覆盖 p 真、p 假，以及 q 假，共 3 项，即 $3/4=75\%$；整体判定只为假，覆盖率 50%。输入表里写了 q 为真，并不表示执行时求值过 q。

不能把本题结果直接套给所有覆盖工具：题目若只考抽象真值表，或工具采用另一种控制流插桩口径，需要按相应定义重新计数。本题专门考察实际原子条件求值。

## 测试层次：正在验证一个部件，还是更大的整体

“在哪个范围测试”与“按黑盒还是白盒选用例”可以自由组合。单元测试能按函数规格做黑盒设计，系统测试也能利用内部结构设计白盒测试，不能一一绑定。

| 测试层次 | 主要对象与目的 | 原创情境 |
| --- | --- | --- |
| 单元／组件测试 | 隔离验证部件自身 | 单独检查手续费计算函数 |
| 组件集成测试 | 部件之间的接口与交互 | 检查转账服务调用记账模块时的参数、返回与异常 |
| 系统测试 | 完整系统的行为与能力 | 在测试环境走完查询、转账、撤销等完整流程 |
| 系统集成测试 | 被测系统与外部系统、服务的接口 | 检查核心系统与外部支付网关对接 |
| 验收测试 | 用户业务需要、部署就绪与接受条件 | 业务方按约定场景确认日终处理满足要求 |

这五层来自 [ISTQB CTFL v4.0.1，第 2.2.1 节](https://istqb.org/wp-content/uploads/2024/11/ISTQB_CTFL_Syllabus_v4.0.1.pdf)。常见教材的“单元、集成、系统、验收”四层划法通常不单列两类集成测试；遇到这类题，先核对它把哪一类接口归入“集成”。

确认测试检查已报告缺陷是否修复；回归测试检查变更是否损害原先可工作的行为，影响可能发生在同一组件、其他组件或相连系统。性能、安全、易用性等是测试类型或质量关注点，也可以在不同层次开展，不能与上述层次放在同一条固定先后链里。

### 原创模拟题 8：接口、验收和回归分别在问什么

下列哪项配对正确？

- A. 单独检查手续费函数输入输出——系统集成测试
- B. 检查应用与外部支付网关的交互——系统集成测试
- C. 修复转账缺陷后检查未改动的查询能力——只能是确认测试
- D. 业务方核对约定业务需求——必定是白盒测试

**答案：B。** 被测应用与外部服务之间的接口属于系统集成关注范围。A 是部件级验证；C 检查变更对其他能力的影响，属于回归目的；D 的业务验收通常以需求和接受条件为依据，不能从测试者身份推成白盒。

如果重跑原先能暴露转账缺陷的测试，目的是确认该缺陷修复；若再检查查询、对账等原有能力，目的就是回归。一个测试套件可以同时服务多个目的，“回归”本身不是独立于单元、系统之外的第五或第六个层次。

## 做选择题前的三次分类

先看生命周期题是在问阶段先后、逐步交付，还是风险驱动；再看 UML 题需要的是结构、消息、活动还是状态；最后把测试的设计依据、覆盖项、测试范围与变更目的分别判断。涉及“必然、全部、只能”的选项，用一个明确的反例检查，通常比背整段定义更可靠。
